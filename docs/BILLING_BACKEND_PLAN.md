## 0. Коротко

- **Подписка привязывается к пользователю** (`subscriptions.user_id`, уникально). Все счётчики — тоже на пользователя.
- **Тарифы:** `start` (0 ₽) и `researcher` (790 ₽/мес). «Курсовая» — тот же `researcher` с разовым периодом 30 дней. «Исследователь» — единственный платный тариф, верхнего нет (решено).
- **Удаление аккаунта с оплаченной подпиской откладывается:** пользователя предупреждают, аккаунт остаётся активным до конца оплаченного периода, затем удаляется, если человек согласился (раздел 4.8).
- **Кто «владелец» опроса.** Опрос лежит в организации, а у организации есть `owner_user_id` (не null, `RESTRICT`). Для личного пространства это сам пользователь. Именно его подписка действует для ответов респондентов. Одно место в коде (`billing_owner_id(survey)`) отвечает за эту связь: если команды появятся позже, менять нужно будет только его.
- **Тарифы лежат в коде** (`app/constants/billing_plans.py`), в БД хранится только код тарифа. Два тарифа не требуют админки.
- **Лимиты проверяет один слой** (`billing_guard`), который вызывается из существующих сервисов. Лимит ИИ и ответов считается атомарным SQL-запросом без гонок.
- **Сначала «теневой режим»**: счётчики и проверки работают, события пишутся в метрики и лог, но ничего не блокируется. 2–4 недели беты дадут реальные токены, потом блокировка включается флагом.
- **Платёжный провайдер не выбран**, поэтому платежи вынесены в отдельный этап 8. До него тариф выдаётся вручную: пользователь отправляет заявку (`plan_requests`), администратор нажимает «Активировать» в админке (раздел 6.1) или выполняет `grant` из CLI.
- **Админка** (`/admin`): таблица пользователей, карточка с подпиской и расходом ИИ, блокировка, отключение ИИ, выдача тарифа и лимитов, заявки на тариф. Роль — существующая колонка `users.role = "admin"` (раздел 6.1).
- Этап 0 нужно сделать **сразу и независимо**: `POST /surveys/ai-builder` сейчас вообще без лимита.

## 2. Модель данных (миграция `037_billing`)

### 2.1. `subscriptions` — одна строка на пользователя

| Поле | Тип | Смысл |
|---|---|---|
| `id` | UUID | |
| `user_id` | UUID, FK `users` `ON DELETE CASCADE`, **unique** | одна подписка на пользователя, текущее состояние |

| `trial_ends_at` | timestamptz, null | |
| `trial_used_at` | timestamptz, null | пробный период выдаётся один раз на пользователя |

Одна строка вместо истории «текущая подписка» упрощает все запросы. История изменений — в `subscription_events`.

### 2.2. `subscription_events` — журнал

`id`, `subscription_id` (FK, `CASCADE`), `kind` (`created`, `trial_started`, `activated`, `renewed`, `plan_changed`, `canceled`, `resumed`, `past_due`, `expired`, `manual_grant`, `admin_override`, `plan_request_approved`, `plan_request_rejected`), `payload` JSONB, `actor_user_id` null, `created_at`. Нужен для поддержки, споров об оплате и подсчёта оттока.

### 2.3. `usage_counters` — счётчики

| Поле | Смысл |
|---|---|
| `user_id` | FK `users` `ON DELETE CASCADE` |
| `metric` | `ai_actions`, `responses` |
| `period_start` | дата начала периода подписки |
| `value` | текущее значение |

Первичный ключ: `(user_id, metric, period_start)`. Остальное (активные опросы, проекты) считается запросом к существующим таблицам с соединением по `organizations.owner_user_id` — отдельные счётчики там не нужны.

### 2.4. `ai_usage_log` — фактический расход ИИ

`id`, `user_id` (FK `users` **`ON DELETE SET NULL`**, чтобы статистика стоимости переживала удаление аккаунта), `survey_id` null, `action` (`survey_build`, `survey_edit`, `ai_summary`, `ai_chat`), `calls` (число вызовов LLM), `model`, `prompt_tokens`, `completion_tokens`, `cost_usd` null, `status` (`ok` / `failed`), `created_at`. Индекс `(user_id, created_at)`.

Это ответ на «не могу посчитать OpenRouter»: через 2–4 недели видно реальную стоимость действия и можно пересчитать разделы 3–5 `PRICING_TARIFFS.md`.

### 2.5. `payments` (этап 8)

`id`, `user_id` (FK `users` **`ON DELETE SET NULL`**: платежи нужны для учёта и после удаления аккаунта), `user_email_snapshot`, `subscription_id` null, `provider`, `provider_payment_id` (**unique**, ключ идемпотентности), `amount_kopecks`, `currency`, `status` (`pending`, `succeeded`, `failed`, `refunded`), `plan_code`, `billing_interval`, `receipt_ref` null, `created_at`, `paid_at`, `raw` JSONB.

### 2.6. Изменения в существующих таблицах

- `survey_responses.locked` bool, default `false` — блокировка ответов сверх квоты. Индекс `(survey_id, locked)`. Добавлено на этапе 4 миграцией `039_response_quota`; существующие ответы остаются видимыми. При откате миграции информация о блокировке теряется (ответы остаются, но снова видны).
- `users.deletion_requested_at` timestamptz, null — согласие пользователя удалить аккаунт после окончания оплаченного периода (4.8). Пусто у всех, кроме тех, кто запросил отложенное удаление.
- Больше ничего в `037_billing` не трогаем (поле `ai_enabled` — в `038_ai_quota`, остальное для админки — в `041_admin`, раздел 2.7). Строки `subscriptions` для существующих пользователей **не создаются миграцией**: они создаются лениво при первом обращении (`ensure_subscription(user)`). Это безопаснее при откате и не требует прохода по всем пользователям.

### 2.7. Миграции `038_ai_quota` (выполнена), `040_subscription_lifecycle` (выполнена) и `041_admin` (админка и заявки на тариф)

### 4.1. Эффективный тариф

Чистая функция `effective_plan(subscription, now) -> Plan`:

| Состояние | Действующий тариф |
|---|---|
| `active`, период не закончился | `plan_code` |
| `trialing`, пробный период не закончился | `plan_code` (по умолчанию `researcher`) |
| `past_due`, прошло менее 3 дней после конца периода | `plan_code` (льготный период) |
| `past_due` дольше 3 дней, `expired`, нет подписки | `start` |

Все остальные модули спрашивают только `get_entitlements(session, user_id)`, который возвращает тариф, лимиты, функции, период и статус; лимиты тарифа переопределяются `subscriptions.limit_overrides`, если администратор задал индивидуальные значения. Состояния не разбираются нигде, кроме этой функции.

### 4.2. Чей тариф и чьи ресурсы

Правило одно, чтобы не размазывать по коду:

- **Действие пользователя** (создать проект, открыть опрос, ИИ, кросстабы, CSV): проверяется тариф **этого пользователя**, ресурсы считаются те, которыми он владеет, то есть лежащие в организациях с `owner_user_id = user.id`.
- **Ответ респондента** (нет пользователя): тариф и счётчик берутся у владельца опроса, `billing_owner_id(survey) = survey.organization.owner_user_id`.

В обычном случае (личное пространство) оба правила дают одного и того же человека. Единственный нетипичный случай — опрос в чужой организации из платформы заявок: проверки идут по действующему пользователю, а ответы идут в квоту владельца организации. Для продукта «проект = один пользователь» это не встречается; при появлении общего доступа к проектам решение придётся пересмотреть (раздел 10).

### 4.3. Периоды и счётчики

- Для платной подписки период двигает успешный платёж (этап 8) или команда `grant`.
- Для «Старта» период скользящий по 30 дней с момента создания подписки; `ensure_current_period` лениво сдвигает его вперёд при обращении, если период закончился. Тик воркера не нужен.
- Ключ счётчика — `current_period_start` подписки. Новый период = новая строка счётчика = обнуление без задач по расписанию.

### 4.4. Атомарное списание без гонок

Резервирование ИИ-действия одним запросом:

```sql
INSERT INTO usage_counters (user_id, metric, period_start, value)
VALUES (:user, 'ai_actions', :period, 1)
ON CONFLICT (user_id, metric, period_start)
DO UPDATE SET value = usage_counters.value + 1
WHERE usage_counters.value + 1 <= :limit
RETURNING value;
```

Нет строки в ответе — лимит достигнут. Параллельные запросы одного пользователя не могут превысить лимит. Возврат при ошибке — `value = GREATEST(value - 1, 0)`.

Для ответов респондентов тот же запрос **без** условия `WHERE`: приём не должен падать, а сверх квоты ответ помечается `locked` (этап 4).

**Как реализовано (этап 4).**

- **Приём ответа** (`survey_service.submit_public_response`): после проверки ответа `billing_guard.register_response` увеличивает счётчик `responses` **владельца опроса** (`survey.organization.owner_user_id`, период берётся из его подписки) тем же запросом без условия и возвращает «заблокирован», если номер превысил `responses_per_period`. Счётчик и ответ пишутся в одной транзакции. Респондент всегда получает «принято»; ответ сверх квоты сохраняется с `locked = true`. Демо-ответы идут в обход приёма и не считаются.
- **Режимы:** без `BILLING_ENABLED` ничего не считается и владелец опроса не читается; в теневом режиме счётчик растёт, переполнение идёт в метрику `svod_billing_limit_hit_total{limit="responses",enforced="false"}`, но ответы не блокируются; блокирует только `BILLING_ENFORCE`.
- **Что скрывает `locked`:** все чтения ответов в `survey_repository` (общее правило `_in_quota()`): списки и страницы с номерами, счётчики опросов, результаты, ответы на открытый вопрос, кросстабы, ИИ, CSV, один ответ по id (для заблокированного 404), соседние ответы, дата последнего ответа. Номера ответов считаются среди видимых. Не скрывает только `count_responses(include_locked=True)`: он нужен проверке «есть ли ответы» перед изменением структуры формы и перед добавлением демо-ответов, потому что заблокированные ответы тоже реальные данные.
- **Разблокировка:** `billing_service.unlock_responses(session, user_id)` открывает **все** заблокированные ответы владельца и пишет событие `responses_unlocked`. Платный тариф даёт доступ ко всему собранному; сколько анализируется, по-прежнему ограничивает тариф (3 000 на опрос). Функцию обязаны вызывать все места, где тариф или лимиты растут: `grant` (этап 5), одобрение заявки и изменение `limit_overrides` (этап 6), платёж (этап 8). Пока оператор может открыть ответы командой `python -m app.billing_cli unlock-responses <почта>`.
- `GET /billing/subscription` отдаёт `usage.locked_responses`. Предупреждение о 80 % квоты придёт вместе с письмами на этапе 5.
- **Новый месяц квоту не снимает:** заблокированные ответы остаются заблокированными, пока тариф не вырастет; новый период даёт свежую квоту только новым ответам.

### 4.5. Учёт ИИ: списание, перехват токенов, возврат

1. `ai_meter` резервирует ИИ-действие **до** вызова LLM.
2. `openrouter_client._request_completion` читает `data["usage"]` и складывает его в `ContextVar`-накопитель. Сигнатура `post_chat_completion` и все остальные вызовы (заявки, Telegram, ТЗ) не меняются. OpenRouter возвращает `usage` (`prompt_tokens`, `completion_tokens`, `cost` в долларах) в каждом ответе сам: параметр `"usage": {"include": true}` устарел и ничего не делает, поэтому в запрос он **не добавляется** (сверено с документацией 2026-10-27). Усечённый ответ и повторный вызов считаются: оба попадают в накопитель и суммируются. Накопитель живёт в `app/services/ai_usage.py`, вне действия `ai_meter` он ничего не собирает.
3. Контекстный менеджер:
   ```python
   async with ai_meter.action(user, ai_meter.ACTION_AI_CHAT, survey_id=survey.id):
       return await survey_ai_analysis_service.chat(...)
   ```
   Сессии БД `ai_meter` открывает сам, короткие и отдельные от запроса: резервирование должно быть видно параллельным запросам до долгого вызова ИИ и не зависеть от коммита вызывающего кода. При выходе пишет строку в `ai_usage_log` и метрики. Если действие упало (502, пустой ответ) или не дошло до ИИ — списание возвращается; упавшее действие всё равно остаётся в журнале со `status = failed`, потому что токены потрачены. Ошибка записи журнала не отменяет уже готовый ответ пользователю.
   Действия: `survey_build`, `survey_edit` (в запросе конструктора уже есть страницы), `ai_summary`, `ai_chat`. Не покрыты, потому что не относятся к сервису опросов: ИИ по заявкам, Telegram, публичные формы и `POST /forms/ai-builder`.
   Что работает всегда, независимо от флагов биллинга: переключатель `users.ai_enabled`, суточный потолок сервиса (если задан) и журнал `ai_usage_log` (нужен, чтобы накапливались реальные токены). Квота месяца и бюджет аккаунта — только при `BILLING_ENABLED`, блокируют — только при `BILLING_ENFORCE`.
4. Если `cost_usd` не пришёл, стоимость считается по токенам и ценам из настроек (`OPENROUTER_PRICE_IN_USD_PER_M`, `OPENROUTER_PRICE_OUT_USD_PER_M`).
5. **Резюме из кэша не списывается**: списание стоит после проверки `stored is not None and not payload.force ...` в `generate_ai_summary`, прямо перед вызовом `generate_summary`.
6. **Потолок расходов в рублях**: перед резервированием проверяется сумма `cost` из журнала за период против `ai_budget_rub_per_period` (защита от смены модели; на премиальной модели «Исследователь» при полном использовании лимита убыточен, см. `PRICING_TARIFFS.md` 5.4) (сумма `cost_usd` умножается на `AI_COST_RUB_PER_USD`, куда входит доплата за пополнение OpenRouter). Бюджет аккаунта при срабатывании даёт `402 limit_reached` с `limit = "ai_budget"` (в теневом режиме только метрика). Отдельно общий суточный потолок сервиса `AI_DAILY_BUDGET_USD` за скользящие 24 часа: при срабатывании `503 {"code": "ai_budget_exceeded"}`, действует всегда, если задан.

### 4.6. Формат ошибок лимитов

`HTTP 402` с `detail`, как уже принято в проекте (`{"code": ..., ...}`):

```json
{
  "code": "limit_reached",
  "limit": "ai_actions",
  "used": 15,
  "max": 15,
  "plan": "start",
  "upgrade_to": "researcher",
  "resets_at": "2026-11-26T10:00:00Z"
}
```

Значения `limit`: `ai_actions`, `ai_budget` (потолок стоимости ИИ в рублях; `used` и `max` тоже в рублях), `active_surveys`, `projects`, `questions`, `feature` (с полем `feature`: `crosstabs` / `csv_export` / `methodology`). Для недоступной функции используется тот же `limit_reached` с `limit = "feature"`: один формат для клиента. Отдельный случай: ИИ отключён администратором (`users.ai_enabled = false`), тогда `403 {"code": "ai_disabled"}`; кнопки ИИ блокируются без предложения тарифа.

### 4.7. Точки встраивания

| Правило | Где | Что проверять |
|---|---|---|
| ИИ-действие | `routes/surveys.py` `build_survey_with_ai` (меняется сигнатура: нужен `CurrentUser`, а не `_user`), `survey_service.generate_ai_summary`, `survey_service.ai_chat` | списание через `ai_meter`, подтверждённая почта, `users.ai_enabled` (иначе 403 `ai_disabled`), всплесковый лимит `_ai_rate_limit` |
| Активные опросы | `survey_service.set_status` при переходе в `open` | число опросов со статусом `open` в организациях пользователя (новая функция репозитория `count_open_for_owner`) против лимита |
| Вопросы | `survey_service.update_survey`, `set_status` | `count_questions(pages)` против `max_questions` |
| Проекты | `survey_service.create_project` | число проектов в организациях пользователя (`count_projects_for_owner`) |
| Ответы | `survey_service.submit_public_response` | счётчик `responses` владельца (этап 4) |
| Потолок анализа | вызовы `list_responses(limit=MAX_RESULTS_ROWS)` в `survey_service` | `limit = min(MAX_RESULTS_ROWS, plan.max_analyzed_responses)` |
| Кросстабы | `survey_service.get_crosstab`; кросстаб внутри `ai_chat` строит сам чат — без функции не отдавать его модели | функция `crosstabs` |
| CSV | `survey_service.export_responses_csv` | функция `csv_export` |
| Фильтр некачественных ответов | `get_results`, `generate_ai_summary`, `ai_chat` | `exclude_flagged = exclude_flagged and has(quality_filter)` |
| Методики | `survey_ai_builder_service.select_methodologies`, `build_survey` (явный список) | на «Старте» только базовые пять (решено): Лайкерт, NPS, CSAT, когнитивное интервьюирование, вопросы-ловушки (`BASIC_METHODOLOGIES` в `billing_plans.py`) |

Правила держатся в `billing_guard` отдельными функциями (`ensure_can_open_survey`, `ensure_can_add_project`, `ensure_feature`, ...), чтобы сервисы вызывали одну строку, а тесты проверяли правило отдельно. Организации, участники и приглашения (`organization_service`, `join_request_service`) **не затрагиваются**.

**Как это реализовано (этап 3).** Без `BILLING_ENABLED` модуль ничего не делает и в БД не ходит; в теневом режиме нарушение правила только считается в `svod_billing_limit_hit_total{limit,plan,enforced="false"}`; при `BILLING_ENFORCE` — `402 limit_reached`. Уточнения к схеме выше:

- **Чей тариф:** действующего пользователя, ресурсы считаются по организациям, где он `owner_user_id` (`count_open_surveys_for_owner`, `count_projects_for_owner`).
- **Проекты:** «приветственный» проект «Добро пожаловать» не считается (его `get_default_project` тоже пропускает). Лимит применяется только к явному `create_project`; проект по умолчанию, который первый опрос получает сам, не отказывается. На «Старте» это значит один свой проект: либо созданный вручную до первого опроса, либо «Мои опросы».
- **Вопросы:** считаются без текстовых блоков (`count_questions`). Правка опроса, который уже длиннее лимита (тариф стал меньше), разрешена, если он не стал длиннее. Публикация опроса длиннее лимита отказывает. ИИ-конструктору лимит сообщается в промпте (`не больше N`), чтобы он не строил то, что нельзя сохранить.
- **Потолок анализа:** тариф анализирует **самые свежие** `max_analyzed_responses` ответов; остальные остаются в базе. Применяется в результатах, списке ответов на открытый вопрос, кросстабе, ИИ-резюме и ИИ-чате (`billing_guard.load_analysis`). Номера ответов в списке остаются настоящими (считаются от общего числа).
- **Фильтр плохих ответов:** на «Старте» ответы только помечаются, из анализа не исключаются (`exclude_flagged` принудительно `false`, пока в выборке есть помеченные ответы).
- **Кросстабы и CSV:** `402` с `limit = "feature"`, `feature = "crosstabs" | "csv_export"`. В ИИ-чате модели на «Старте» кросстаб не строится и не показывается (`allow_crosstab=False`).
- **Методики:** ручной выбор не входящих в базовый набор даёт `402` (`feature = "methodology"`, список в поле `methodologies`) до списания ИИ-действия. При автоподборе модель видит урезанный каталог (только доступные методики и направления, где они есть).
- `GET /billing/subscription` отдаёт ещё и `usage.active_surveys` и `usage.projects`.

**Известные ограничения.**

- Методики, добавленные в форму вручную через интерфейс (без ИИ), сервер не проверяет: проверяется только ИИ-конструктор. Каталог `GET /methodologies` пока не помечает закрытые методики, это для этапа 7.
- Если на «Старте» видимых ответов больше потолка анализа (за несколько месяцев набралось больше 100), сохранённое ИИ-резюме считается устаревшим всегда: оно сравнивается с числом всех видимых ответов, а анализ идёт по свежим N. Квота этапа 4 этого не снимает, потому что у неё период месяц, а потолок анализа действует на опрос целиком.
- Сравнения по сегментам внутри ИИ-резюме строятся тем же кодом, что кросстаб, и от функции `crosstabs` не зависят.

### 4.8. Удаление аккаунта

Сейчас `POST /auth/me/delete` с паролем сразу вызывает `account_deletion_service.delete_account`, подписка, счётчики и журнал событий уходят каскадом. Правило нового поведения: **если у пользователя есть оплаченный период, аккаунт сразу не удаляется.**

**Оплаченный период** — подписка в статусе `active` на `researcher` с `current_period_end > now`, включая разовую «Курсовую». Пробный период и `past_due` оплаченными не считаются: такие аккаунты удаляются сразу, как сейчас, но перед этим отключается автопродление.

Поток:

1. Пользователь вводит пароль, `POST /auth/me/delete {password}`.
2. Оплаченного периода нет — удаление как сейчас (204). Перед ним вызывается `subscription_lifecycle_service.cancel_for_account_deletion` (автопродление выключается, на этапе 8 рекуррентная подписка отменяется у провайдера, чтобы деньги не списывались с удалённого аккаунта).
3. Оплаченный период есть — **предупреждение**: `409 {"code": "active_subscription", "plan": "researcher", "current_period_end": "...", "can_defer": true}`. Ничего не удалено и не изменено.
4. Фронтенд показывает окно: «У вас действует подписка до {дата}. Аккаунт останется активным до этой даты, затем будет удалён». Кнопки: «Отмена» и «Согласен».
5. «Согласен» — тот же запрос с `defer_until_subscription_ends: true` (поле добавляется в `DeleteAccountRequest`, пароль вводится снова). Сервер ставит `users.deletion_requested_at = now`, `cancel_at_period_end = true` (автопродление выключено сразу), пишет событие `deletion_scheduled` и отвечает `202 {"status": "scheduled", "delete_at": "<current_period_end>"}`. Это и есть согласие пользователя.
6. Пока идёт период, аккаунт **полностью работает**: вход, опросы, сбор ответов, ИИ в пределах квот. Интерфейс показывает плашку «Аккаунт будет удалён {дата}. Отменить». Признак `deletion_scheduled` приходит в `GET /billing/subscription` и в `GET /auth/me`.
7. Отмена: `POST /auth/me/delete/cancel` очищает `deletion_requested_at`, пишет событие `deletion_canceled`. Автопродление **не включается обратно**: пользователь сам нажимает «Возобновить» (`POST /billing/resume`), ответ отмены подсказывает это.
8. Напоминания: письмо за 7 дней и за 1 день до даты со ссылкой «Отменить удаление». Дедупликация через события `deletion_reminder_7d` и `deletion_reminder_1d` в `subscription_events`.
9. По окончании периода тик воркера (5.3) находит пользователей с `deletion_requested_at` и истёкшим периодом (`current_period_end <= now` или `status = expired`) и выполняет удаление. Пароль на этом шаге не нужен: согласие уже получено на шаге 5. Письмо «аккаунт удалён» уходит на сохранённый адрес.

Дополнительные правила:

- Пока удаление запрошено, оплата через чекаут блокируется: `409 {"code": "deletion_scheduled"}` («сначала отмените удаление»). Продление администратором через `grant` сдвигает `current_period_end`, и удаление переносится вместе с ним автоматически.
- Если к моменту удаления у пользователя есть организация с другими участниками (существующая проверка `delete_account` отвечает 409), удаление не выполняется: пользователю уходит письмо «передайте владение или удалите организацию, затем повторите удаление», `deletion_requested_at` очищается, пишется событие `deletion_blocked`.
- Возврат остатка не предусмотрен: пользователь получил весь оплаченный период.

Рефакторинг: из `delete_account` выделяется `purge_account(session, user)` — всё, что идёт после проверки пароля (сбор ключей файлов, удаление заявок, содержимого организаций, приглашений, пользователя, очистка хранилища). Его вызывают `delete_account` (немедленное удаление) и воркер (отложенное).

Что остаётся после удаления:

- `payments` (`user_id` → `SET NULL`, остаётся `user_email_snapshot`): нужны для налогового учёта;
- `ai_usage_log` (`user_id` → `SET NULL`): статистика стоимости сохраняется;
- подписка, счётчики и события удаляются каскадом.

## 5. Жизненный цикл подписки

### 5.1. Переходы

| Из | Событие | В |
|---|---|---|
| нет | первое обращение пользователя | `active` / `start` |
| `start` | пользователь запускает пробный период | `trialing` / `researcher`, 14 дней |
| `trialing` | оплата | `active` |
| `trialing` | прошло 14 дней без оплаты | `expired` → действует `start` |
| `active` | период закончился, автопродление включено, платёж прошёл | `active`, новый период |
| `active` | период закончился, платёж не прошёл | `past_due`, льгота 3 дня |
| `past_due` | оплата прошла | `active` |
| `past_due` | льгота кончилась | `expired` |
| `active` | отмена | `cancel_at_period_end = true`, по концу периода → `expired` |
| `active` (`one_off`) | конец периода | `expired` без продления |
| любое | `grant` из CLI | `active` на указанный срок |

Пробный период один на пользователя (`trial_used_at`). Условие запуска: подтверждённая почта. Защита от повторных пробных периодов через новые аккаунты — только подтверждение почты и обычные лимиты на регистрацию; полной защиты нет.

### 5.2. Понижение

`enforce_downgrade(user)` вызывается при переходе в `expired`:

- Опросы сверх лимита активных переводятся в `closed` (остаются самые недавно активные). Ничего не удаляется, ответы и ссылки сохраняются.
- Проекты и вопросы сверх лимита **не удаляются**: блокируется только создание нового.
- Хранение данных после окончания: 90 дней, дальше предупреждение. Автоудаление в этом плане не делается, это отдельное решение с юристом.

### 5.3. Воркер

В `worker.py` добавлен тик по образцу `overdue_tick`: раз в `BILLING_TICK_SECONDS` (300 с), только при `BILLING_ENABLED`, три шага, каждый в своей сессии (сбой одного не останавливает остальные): `subscription_lifecycle_service.process_due`, `account_deletion_service.process_scheduled_deletions`, `account_deletion_service.send_deletion_reminders`.

Подписки выбираются по одной через `SELECT ... FOR UPDATE SKIP LOCKED` с постраничным курсором по `id`, коммит после каждой: два воркера не обработают одну строку, пропущенная строка не зацикливает тик, сбой одной подписки не откатывает остальные. Проверено на PostgreSQL: два тика одновременно закрыли 6 подписок ровно по одному разу.

Письма идут через `email_service.send_notice`, тексты собраны в `billing_mail.py`. Уведомления в интерфейсе **не используются**: в режиме сервиса опросов колокольчик скрыт (`IS_SURVEYS_APP`), единственный реальный канал — почта.

### 5.4. Ручное управление

`python -m app.billing_cli`:

- `grant <почта> (--days N | --until ГГГГ-ММ-ДД) [--plan researcher] [--note "счёт №…"]` — выдать тариф (оплата по счёту, подарок, компенсация). `--days` прибавляется к действующему периоду, `--until` ставит дату и не сокращает более длинный период;
- `grant-beta --until ГГГГ-ММ-ДД [--dry-run]` — выдать всем активным аккаунтам платный тариф до даты (бета-доступ); у кого уже есть тариф на этот срок или дольше, пропускается; `--dry-run` только считает;
- `show <почта>` — тариф, статус, период, использование, скрытые ответы, последние события (только чтение).

`grant` пишет событие `manual_grant` (с пометкой и автором) и открывает ответы, которые держала квота (раздел 4.4).

### 5.5. Как реализовано (этап 5)

**Перевод закончившейся подписки в бесплатную** (`expire_subscription`): запись остаётся той же, но становится `start / active / none`, с новым бесплатным окном на 30 дней, **начинающимся в момент окончания доступа**; индивидуальные лимиты и поля провайдера сбрасываются; метка пробного периода остаётся. После этого `enforce_downgrade` закрывает опросы сверх трёх (остаются самые активные: последний ответ, иначе последняя правка). Ничего не удаляется. Событие `expired` с причиной (`trial_ended`, `period_ended`, `grace_over`).

**Что в тике делается с подпиской.** Закончились: пробный период, период платного тарифа, льгота после неудачной оплаты. Автопродляемую подписку с провайдером (`provider` задан, продление не отключено, не разовая) воркер не трогает: это забота платёжного потока (этап 8). Напоминания: за 2 дня до конца пробного, за 3 дня до конца платного периода (по одному на период, дедупликация через `subscription_events`). Письмо о конце срока уходит после коммита; если письмо не ушло, оно не повторяется, а вот напоминания и предупреждения повторяются на следующем тике, пока почта не заработает (без SMTP момент помечается обработанным).

**Предупреждение о 80 % лимита** (ИИ-действия и ответы): ставится в очередь в момент, когда счётчик пересекает порог (`warn_if_near_limit`, событие `limit_warning` с `sent = false`), отправляется воркером, не в запросе. Только при `BILLING_ENFORCE`; один раз на метрику и период; для лимитов меньше 5 не отправляется. Невысланное письмо повторяется сутки, потом бросается.

**Пробный период** (`POST /billing/trial`): 14 дней (`BILLING_TRIAL_DAYS`) тарифа «Исследователь», один раз на человека (`trial_used_at`), при подтверждённой почте (если сервер умеет слать почту). Скрытые ответы пробный период **не открывает**, их открывает только платный тариф.

**Отмена и возобновление** (`POST /billing/cancel`, `POST /billing/resume`): отключают и включают продление; тариф работает до конца периода. Возобновить нельзя, пока запланировано удаление аккаунта (409 `deletion_scheduled`). Ошибки состояний: `nothing_to_cancel`, `nothing_to_resume`, `trial_used`, `already_subscribed`, `billing_disabled`.

**`grant`** (`subscription_lifecycle_service.grant`): выдаёт разовый период (`one_off`), продлевает действующий, открывает скрытые ответы, при запланированном удалении оставляет продление выключенным: дата удаления следует за концом периода и сдвигается вместе с ним.

**Отложенное удаление аккаунта** (раздел 4.8) реализовано как описано, с уточнениями:
- `POST /auth/me/delete` отвечает 204 (удалён), 409 `active_subscription` (с `can_defer`), 202 `{status: "scheduled", delete_at}` или 409 со строкой про организации с участниками; `POST /auth/me/delete/cancel` отвечает 204 всегда;
- признак «удаление запланировано» отдаёт **`GET /billing/subscription`** (`deletion_scheduled`, `deletion_at`); **в `GET /auth/me` он не добавлен**: профиль читается слишком часто и не должен ходить за подпиской;
- напоминания за 7 и 1 день: отправляется ближайшее из подходящих (не оба сразу), и ни одного, если удаление запросили слишком поздно для напоминания; дедупликация по дате удаления, поэтому после продления напоминания приходят заново;
- удаление в воркере проверяет организации с другими участниками ещё раз; если они появились, флаг снимается, пишется `deletion_blocked`, человеку уходит письмо;
- платёж-провайдер и отмена рекуррентной подписки у него (`cancel_for_account_deletion`) подключаются на этапе 8; блокировка оплаты при запланированном удалении (409 `deletion_scheduled`) тоже появится вместе с чекаутом.

**Что не сделано и почему.** Состояние `past_due` и повторные попытки оплаты появятся с платежами (этап 8), сейчас воркер учитывает льготу, если такой статус уже есть. Письма ссылаются на `/profile?tab=subscription`: страница с вкладкой есть, но вкладка «Подписка» остаётся заглушкой до этапа 7.

## 6. HTTP-интерфейс

Методы `/billing/*` работают с текущим пользователем, параметра «организация» нет. Управлять подпиской можно только своей. Исключение — админка (раздел 6.1), она доступна только роли `admin`.

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /billing/plans` | публичный | каталог тарифов для страницы цен |
| `GET /billing/subscription` | авторизованный | тариф, статус, период, пробный период, использование и лимиты (ИИ, ответы, активные опросы, проекты), число заблокированных ответов, заявка в ожидании, признак отложенного удаления аккаунта |
| `POST /billing/trial` | авторизованный | запустить пробный период |
| `POST /billing/plan-requests` | авторизованный | заявка на подключение тарифа `{plan, interval, contact, comment}`; письмо администратору на `ADMIN_NOTIFY_EMAIL`; пока есть заявка в `pending`, новая не принимается (409) |
| `POST /billing/checkout` | авторизованный | `{plan, interval}` → `{payment_url}` (этап 8) |
| `POST /billing/cancel`, `POST /billing/resume` | авторизованный | отмена и возобновление автопродления |
| `GET /billing/payments` | авторизованный | история платежей |
| `POST /auth/me/delete` (существующий, расширяется), `POST /auth/me/delete/cancel` | авторизованный | удаление аккаунта; при оплаченном периоде 409 `active_subscription` либо, с согласием, 202 и отложенное удаление; отмена отложенного удаления (4.8) |
| `POST /billing/webhooks/{provider}` | провайдер | вебхук с проверкой подписи и идемпотентностью (этап 8) |

Роутер подключается в `api/routes/__init__.py`.

### 6.1. Админка и заявки на тариф

Пока оплата ручная, администратор видит пользователей, выдаёт тариф по заявке и может отключить ИИ или заблокировать аккаунт.

**Доступ.** `users.role = "admin"` (колонка уже есть, сейчас не читается). Зависимость `AdminUser` в `api/deps.py` проверяет роль по базе, а не по токену, поэтому снятие роли действует сразу. Администратором нельзя стать через API: первого назначает CLI (`make-admin`). Нельзя заблокировать себя и последнего администратора. Роль возвращается в `GET /auth/me`. Каждое действие администратора пишется в `subscription_events` с `actor_user_id`.

| Метод и путь | Назначение |
|---|---|
| `GET /admin/users` | серверная пагинация, поиск по email и имени, фильтры (тариф, статус подписки, почта подтверждена, активен), сортировка. Колонки: имя, email, телефон, почта подтверждена, регистрация, последний вход, активен, роль, тариф и статус, дата окончания, ИИ-действий использовано/лимит, опросов, ответов, «удаление запрошено». Хеш пароля не отдаётся |
| `GET /admin/users/{id}` | карточка: подписка, события, последние 50 записей `ai_usage_log`, заявки, лимиты |
| `PATCH /admin/users/{id}` | `is_active` (блокировка уже работает через `deps.get_current_user`: 401 неактивному), `ai_enabled` |
| `POST /admin/users/{id}/subscription`, `DELETE` | выдать тариф `{plan, days, note, limit_overrides}` через `subscription_lifecycle_service.grant`; `DELETE` возвращает на «Старт» |
| `GET /admin/plan-requests`, `POST /admin/plan-requests/{id}/approve`, `.../reject` | заявки; `approve` вызывает `grant` на период из заявки и пишет `plan_request_approved`; повторный `approve` ничего не создаёт |
| `GET /admin/stats` | пользователи (всего, новые за 7 и 30 дней, активные за 30), платящие по тарифам, ожидаемая выручка, расход ИИ за месяц по `ai_usage_log` и его доля от дохода, заявки в ожидании |

**Интерфейс.** Маршрут `/admin` в режиме surveys, защищённый `AdminRoute`; вкладки «Пользователи», «Заявки на тариф», «Сводка»; таблица с серверной пагинацией, по клику `Drawer` с карточкой и действиями. Пункт «Администрирование» в меню профиля виден только администратору.

**Персональные данные.** Email и телефон всех пользователей видит только администратор; риск описан в разделе 10.

### 6.2. Как реализовано (этап 6)

- **Миграция `041_admin`**: `users.last_login_at`, индекс `users(created_at)` (сортировка таблицы), таблица `plan_requests` с частичным уникальным индексом «одна заявка `pending` на человека»; в таблице добавлено поле `decision_note` (причина отказа или заметка при активации). `last_login_at` ставит `auth_service.login` после успешной проверки пароля.
- **Весь `/admin` закрыт одной зависимостью на роутере** (`APIRouter(dependencies=[Depends(get_admin_user)])`): новый маршрут нельзя оставить открытым по ошибке. Роль читается из базы на каждый запрос.
- **Фильтр по тарифу** один параметр `tier`: `free` (в том числе человек без строки подписки и платный с истёкшим периодом, которого воркер ещё не перевёл), `paid`, `trial`, `past_due`. Условия построены от текущего времени и повторяют `effective_plan_code`. Сортировка по `plan_ends_at` идёт по дате конца **действующего** платного тарифа, у бесплатных пусто.
- **Чтение ничего не пишет**: у человека без строки подписки карточка показывает «Старт», строка не создаётся.
- **Опросы и ответы в таблице** не считают пример «Добро пожаловать» и скрытые квотой ответы (то же правило, что у лимита проектов).
- **Блокировка и ИИ**: `PATCH` пишет события `account_blocked`, `account_unblocked`, `ai_disabled`, `ai_enabled` с администратором в `actor_user_id`. Нельзя заблокировать себя (`cannot_block_self`) и последнего администратора (`last_admin`).
- **Выдача и снятие тарифа**: `POST /admin/users/{id}/subscription` вызывает тот же `grant`, что и консоль; неизвестные или отрицательные личные лимиты — `422`. `DELETE` переводит на «Старт» сразу (окно «Старта» начинается с этого момента), закрывает лишние опросы и пишет `admin_revoked`. Если у человека запланировано удаление аккаунта, снятие тарифа отказывается (`deletion_scheduled`): иначе воркер удалил бы аккаунт.
- **Заявки**: `POST /billing/plan-requests` (контакт обязателен, одна ожидающая на человека, атомарно через `ON CONFLICT` по частичному индексу; письмо на `ADMIN_NOTIFY_EMAIL`, если задан). `GET /billing/subscription` отдаёт `plan_request` с ожидающей заявкой. `approve` берёт строку заявки `FOR UPDATE`, поэтому пять параллельных нажатий дают одно подключение (остальные `409 plan_request_processed`); срок по умолчанию 30 дней (месяц и пакет «Курсовая») или 365 (год), администратор может назвать свой. События `plan_request_created`, `plan_request_approved`, `plan_request_rejected`. Письма человеку уходят после коммита.
- **Сводка**: ожидаемая выручка — активные платные подписки без пробных: месяц по цене месяца, год по 1/12 годовой цены, выданные вручную (`one_off`) по цене месяца. Доля ИИ — расход за 30 дней в рублях по `AI_COST_RUB_PER_USD` к этой выручке.
- **Интерфейс**: `src/pages/AdminPage.tsx` (вкладки в адресе `?tab=requests|stats`), `src/components/admin/*`, `src/shared/api/admin.api.ts`. `AdminRoute` в `App.tsx` отправляет не-администратора на главную; пункт «Администрирование» в меню профиля виден только администратору в режиме surveys.
- **Проверено** на реальной PostgreSQL (миграция вверх и вниз на данных, 22 сценария через настоящее приложение: доступ, фильтры, сортировки, пагинация, параллельные нажатия) и в браузере (таблица, карточка, переключатель ИИ, активация заявки, сводка, обычный пользователь на `/admin`).
- **Не сделано**: отправка писем администратору при ошибках платежей (этап 8). Вкладка «Подписка» и форма заявки у самого человека сделаны на этапе 7 (раздел 6.3).

### 6.3. Как реализовано (этап 7, интерфейс тарифов)

Только фронтенд, режим surveys; бэкенд не менялся.

- **Данные о тарифе** лежат в одном контексте (`SubscriptionProvider` в `AppLayout`, хук `useSubscription`): `GET /billing/subscription` читается при входе и после каждого ИИ-действия и после каждого отказа 402. Вне сервиса опросов провайдер ничего не запрашивает, хук отдаёт «тарифов нет».
- **Вкладка «Подписка»** (`components/profile/ProfileSubscriptionTab.tsx`, заглушка из `ProfileFutureTabs.tsx` удалена): тариф, статус, срок, цена, использование за период (ИИ-действия, ответы, открытые опросы, проекты), скрытые ответы сверх квоты, предупреждения (продление отключено, удаление аккаунта запланировано, пробный период). Действия: пробный период на 14 дней (один раз), запрос подключения или продления, отключить и возобновить продление. Пока лимиты в теневом режиме, вкладка так и говорит.
- **Форма заявки** (`PlanRequestModal`): срок (месяц, год, пакет «Курсовая») с ценами из `GET /billing/plans`, контакт (по умолчанию почта), комментарий. После отправки кнопка превращается в «Заявка отправлена», повторная заявка невозможна (на сервере `409`). Тексты отказов берутся из `detail.message` или по коду.
- **Страница `/plans`** (в меню профиля «Тарифы»): карточки «Старт», «Исследователь», пакет «Курсовая» и таблица сравнения. Всё строится из каталога `GET /billing/plans`, то есть из тех же цифр, что применяет сервер; ничего сверх каталога не обещается. Публичной (без входа) страницы пока нет.
- **Окно «лимит достигнут»** (`PaywallModalHost`): клиент API (`shared/lib/api.ts`) на любой `402 limit_reached` рассылает событие, окно показывает причину по-русски (ИИ-действия, открытые опросы, проекты, вопросы, закрытая функция) и ведёт на `/plans` (или в «Подписку», если выше тарифа нет). Работает для любого экрана без правок в нём.
- **Счётчик у ИИ-кнопок** (`AiQuotaNote`): «Осталось N из M ИИ-действий» в конструкторе опросов, в чате по результатам и у кнопки ИИ-резюме; при остатке до 20 % подсветка и ссылка на тарифы; когда лимит выбран и он включён (`enforced`), поле ввода и кнопки отключены, показана ссылка «Выбрать тариф». Конструктор форм основного СВОД не затронут.
- **Ошибки ИИ в тексте** (`shared/lib/billingErrors.ts`): 402, 403 `ai_disabled`, 503 `ai_budget_exceeded` превращаются в понятную фразу в тех трёх местах, где раньше показывалась общая ошибка.
- **Проверено** в браузере на реальном бэкенде с `BILLING_ENFORCE=true`: вкладка у бесплатного и пробного пользователя, заявка (запись в БД, баннер), пробный период, страница тарифов, окно после настоящего ответа 402, блокировка ввода и предупреждение «осталось 2 из 15».
- **Не сделано**: уведомления о 80 % лимита в самом интерфейсе (письмо есть), публичная страница тарифов без входа. Оплата сделана на этапе 8 (раздел 6.4).

### 6.4. Как реализовано (этап 8, онлайн-оплата через ЮKassa)

Решение владельца: самозанятый (НПД), провайдер ЮKassa. Проверено по документации ЮKassa: самозанятым доступна интеграция по API, уведомления подтверждаются проверкой адреса и повторным запросом платежа (подписи запроса нет), платёж создаётся с заголовком `Idempotence-Key`.

- **Разовые платежи, без автосписаний.** Рекуррентные платежи (автоплатежи) для самозанятых в документации не подтверждены, поэтому человек платит за каждый срок отдельно: месяц (790 ₽), год (7 900 ₽) или пакет «Курсовая» (490 ₽, 30 дней). Оплаченный срок добавляется к действующему через тот же `grant`, что и ручная выдача; в `grant` добавлен параметр `interval`, чтобы месяц и год попадали в сводку выручки правильно. Напоминание о конце тарифа за 3 дня уже есть (этап 5). Кнопки «Отключить/Возобновить продление» из вкладки убраны: продлевать автоматически нечего (эндпоинты `/billing/cancel` и `/billing/resume` остались).
- **Данные**: таблица `payments` (миграция `042_payments`): одна строка на попытку, `idempotence_key` и `(provider, provider_payment_id)` уникальны, `applied_at` ставится один раз. `user_id` с `SET NULL` и `payer_email`: запись о деньгах переживает удаление аккаунта.
- **Правило безопасности**: платёж закрывается только по тому, что сам сервер получил от API ЮKassa (`GET /payments/{id}`), а не по уведомлению или по возврату человека в браузере. Уведомление лишь называет платёж, на который нужно посмотреть. Адрес отправителя проверяется (`YOOKASSA_VERIFY_WEBHOOK_IP`), но это вторая линия защиты. Сумма и валюта у провайдера сверяются с нашими: расхождение ставит статус `mismatch`, тариф не выдаётся, администратору уходит письмо.
- **Идемпотентность**: строка платежа берётся `FOR UPDATE`, `applied_at` проставляется один раз, поэтому пять параллельных уведомлений, опрос worker и возврат человека на страницу продлевают тариф ровно один раз.
- **Создание платежа** (`POST /billing/checkout`): строка записывается и коммитится до обращения к ЮKassa (сбой посередине оставляет след, а не потерянные деньги), затем вызов с `Idempotence-Key`. Повторный клик по «Оплатить» в течение 30 минут возвращает ту же страницу оплаты. Недоступная ЮKassa даёт `503`, отказ провайдера (обычно неверные ключи) — `502` с предложением оставить заявку; оба случая оставляют строку `failed` для администратора и не показываются человеку в истории.
- **Эндпоинты**: `POST /billing/checkout`, `GET /billing/payments`, `GET /billing/payments/{id}` (опрашивает ЮKassa сам, чтобы тариф включился сразу, даже если уведомление запаздывает), `POST /billing/webhooks/yookassa` (открытый, `200` при любом исходе, на который повтор не повлияет; `503`, если API ЮKassa недоступен, тогда ЮKassa повторяет до суток). `GET /billing/plans` отдаёт `payments_enabled`.
- **Worker** (`payment_service.reconcile_open`, шаг тика): неоплаченные платежи старше 2 минут спрашиваются у ЮKassa (до `PAYMENT_PENDING_GIVE_UP_HOURS`), платёж, о котором провайдер так и не ответил за 15 минут, списывается как `failed`. Потерянное уведомление не оставляет заплатившего без тарифа.
- **Возвраты**: уведомление `refund.succeeded` (или опрос) записывает `refunded_kopecks`, событие `payment_refunded` и письмо администратору; тариф не снимается сам, это решение человека.
- **Заявка и оплата**: оплата закрывает ожидающую заявку человека («Оплачено онлайн»), чтобы её не активировали второй раз. Заявка на счёт остаётся запасным путём.
- **Администратор**: в карточке вкладка «Платежи» (статус, сумма, `ID в ЮKassa`, причина), в сводке «Получено онлайн за 30 дней» (возвраты вычтены, тестовые платежи не считаются), события платежей в журнале. Метрика `svod_payments_total{outcome}`.
- **Интерфейс**: кнопка «Оплатить» (выбор срока, переход на страницу ЮKassa), «Нужен счёт? Оставить заявку», после возврата `?payment=<id>` вкладка опрашивает платёж и пишет «Оплата прошла, тариф включён», «Оплата не прошла» или «Оплата ещё обрабатывается»; история платежей.
- **Проверено**: 755 юнит-тестов; 13 сценариев на реальной PostgreSQL через настоящее приложение с поддельной ЮKassa за настоящим HTTP-клиентом (в том числе пять параллельных уведомлений, поддельное уведомление, потерянное уведомление, недоступная ЮKassa, возврат, несовпадение суммы, удаление аккаунта); в браузере весь путь «Оплатить → страница оплаты → вернулись», а также отмену оплаты. С настоящей ЮKassa не проверялось: ключей нет, поэтому первая оплата в тестовом магазине обязательна (RUNBOOK, «Приём платежей»).
- **Не выяснено и не сделано**: чеки самозанятого (кто и как их формирует: см. RUNBOOK), комиссия и автоплатежи для самозанятых, публичная оферта (нужна до приёма денег), возврат из интерфейса (делается в кабинете ЮKassa), защита от двух параллельных платёжных страниц при одновременном клике из двух вкладок (оба платежа корректны и оба продлят тариф).

### 6.5. Как реализовано (этап 9, подготовка к запуску)

Пошаговый порядок и откат — [LAUNCH_CHECKLIST.md](./LAUNCH_CHECKLIST.md). Здесь только то, что добавлено в код.

- **`billing_cli preflight`**: проверка готовности с кодом выхода `1` при критичных замечаниях. Смотрит: тарифы включены, `SECRET_KEY`, почта, публичный адрес, `ADMIN_NOTIFY_EMAIL`, потолок расходов на ИИ, слежение за балансом OpenRouter, ключи ЮKassa, наличие администратора, версия миграций БД против кода, накопленный в теневом режиме счётчик ответов, есть ли кто-то на платном тарифе, заявки, скрытые ответы, платежи без итога.
- **`billing_cli reset-response-counters [--dry-run]`**: обнуляет счётчик ответов теневого режима. Нужен, потому что в теневом режиме ответы считаются в тот же счётчик, и без сброса они лягли бы на квоту в момент включения.
- **`billing_cli funnel --days N`**: воронка зарегистрировавшихся за период: почта, первый опрос, первый ответ, пробный период, оплата, платный тариф сейчас (аналитика запуска, `PRICING_TARIFFS.md` 8.5).
- **Оповещения** (`ops_alert_service`, шаг тика worker): ИИ не отвечает (за 30 минут не меньше 10 действий и половина с ошибкой), суточный потолок расходов на ИИ (80 % и 100 %), кредиты OpenRouter (нужен `OPENROUTER_MANAGEMENT_KEY`, проверка раз в 30 минут), платежи не создаются (3 за час), платежи без итога больше часа. Письмо на `ADMIN_NOTIFY_EMAIL` и строка `ERROR … Ops alert` в логе; один и тот же ключ не чаще раза в `OPS_ALERT_COOLDOWN_MINUTES`, состояние в памяти worker.
- **Исправление, найденное при подготовке: адрес респондента.** Uvicorn запущен без доверия к заголовкам прокси, поэтому `request.client.host` у всех посетителей был адресом nginx, и лимит приёма ответов (40 за 3 минуты на пару «опрос и адрес») на деле работал как один лимит на весь опрос: на популярном опросе остальным отвечало «Слишком много запросов». Теперь `app/core/client_ip.py` берёт адрес из `X-Real-IP` (его выставляет nginx, перезаписывая присланное клиентом), и только если запрос пришёл с частного адреса, то есть от нашего прокси; запрос напрямую из интернета не может выбрать себе адрес заголовком. Применено к приёму ответов, подсказкам форм, подсказкам адресов и вебхуку ЮKassa. `X-Forwarded-For` намеренно не используется: его присылает и клиент.
- **Нагрузочный скрипт** `backend/scripts/load_public_survey.py` (открыть опрос и отправить ответ, много людей сразу, исходы и задержки; `--distinct-ips` даёт каждому запросу свой адрес и работает только изнутри сети Docker напрямую в API). **Резервные копии** `scripts/backup-db.sh` (дамп во временный файл, проверка, переименование, ротация; код выхода `1` и никакого файла при сбое).
- **Проверено**: 803 юнит-теста; на реальной PostgreSQL через настоящее приложение и нагрузочный скрипт: с одного адреса принято ровно 40 из 60 (остальные 429); 150 человек с разными адресами при 30 одновременных в теневом режиме приняты все, счётчик 190 и ни одного скрытого ответа; `preflight` предупредил о накопленном счётчике; сброс обнулил его; после включения лимитов 150 человек при 30 одновременных приняты все 201, скрыто ровно 50 сверх квоты в 100, счётчик 150; `funnel` посчитал. Резервный скрипт проверен на одноразовой БД: дамп читается, сбой оставляет код 1 и не оставляет файла, старая копия удаляется.
- **Не сделано**: внешний мониторинг (нужен сторонний сервис, настраивается на стороне владельца), cron на сервере, юридические документы, проверка настоящей ЮKassa.

## 9. Тесты

Подход проекта — `unittest` с `AsyncMock`/`patch`. По этапам:

| Этап | Что проверять |
|---|---|
| 0 | `ai-builder` возвращает 429 при превышении всплесков и 403 при неподтверждённой почте |
| 1 | `effective_plan` на всех состояниях и границах времени (чистая функция); неизвестный код тарифа → `start`; ленивое создание подписки; `billing_owner_id` |
| 2 | резервирование и возврат при ошибке LLM; резюме из кэша не списывается; суммирование usage при повторном вызове; расчёт стоимости по токенам; срабатывание потолка расходов; теневой режим не блокирует, но пишет метрику |
| 3 | каждое правило из 4.7 на границе (N−1, N, N+1), формат ошибки 402 |
| 4 | ответ принимается при исчерпанной квоте и помечается `locked`; заблокированные не попадают в результаты, экспорт и ИИ; разблокировка при повышении; демо-ответы не считаются |
| 5 | таблица переходов из 5.1, один пробный период на пользователя, понижение не удаляет данные, `process_due` идемпотентен. Удаление аккаунта: без оплаченного периода удаляет сразу и отключает автопродление; с оплаченным отвечает 409 `active_subscription` и ничего не меняет; с согласием отвечает 202, ставит `deletion_requested_at`, выключает автопродление, аккаунт продолжает работать; отмена очищает флаг и не включает автопродление; чекаут при запрошенном удалении блокируется; напоминания за 7 и 1 день не дублируются; воркер не трогает аккаунт до конца периода и удаляет после; организация с участниками блокирует удаление с письмом; платежи остаются после удаления |
| 6 | не админ получает 403 на всех `/admin/*`, роль читается из БД, а не из токена; нельзя заблокировать себя и последнего администратора; `approve` создаёт подписку и пишет `plan_request_approved`, повторный не создаёт вторую; `ai_enabled = false` даёт 403 `ai_disabled`; список пользователей не содержит `password_hash` |
| 8 | повторная доставка вебхука не создаёт второй платёж, неверная подпись отклоняется, рекуррентное списание переводит `past_due` → `active` |

Что нельзя проверить моками: **атомарность SQL из 4.4**. Для неё нужен интеграционный тест на реальном PostgreSQL (например, 50 параллельных резервирований при лимите 10 → ровно 10 успехов). Тест запускается, только если задана переменная `TEST_DATABASE_URL`, иначе пропускается. Это отдельная небольшая инфраструктурная задача.

Команда проверки из проекта (из каталога `backend/`, нужен любой `OPENROUTER_API_KEY`):

```bash
python -m unittest discover -s tests -t .
```

## 10. Риски и ограничения

| Риск | Что с этим делать |
|---|---|
| Блокировка ответов (`locked`) затрагивает много запросов | единая функция условия в `survey_repository` и тест на каждый путь чтения; этап 4 после 3 и отдельным релизом |
| Лимит ответов в первый период после включения может «запереть» уже собранные ответы бета-пользователей | блокировка работает только при `BILLING_ENFORCE`, ответы до включения не блокируются (у них `locked = false`). Но счётчик теневого режима уже содержит ответы текущего периода, поэтому **перед включением `BILLING_ENFORCE` обнулить счётчик ответов** (`DELETE FROM usage_counters WHERE metric = 'responses'`), а бета-доступ выдать до этого (раздел 5.4) |
| Утечка `ContextVar` между задачами | накопитель создаётся только внутри `ai_meter.action` и сбрасывается в `finally`; вне него `usage` игнорируется |
| Несколько процессов API | всплесковый лимит в памяти остаётся приблизительным (как сейчас); месячные квоты — в БД и точные |
| Параметр OpenRouter для возврата стоимости не проверен | запасной расчёт по токенам и ценам из настроек (4.5, п. 4) |
| Допущение «проект = один пользователь» нигде не закреплено в БД | всё держится на `billing_owner_id` и на правиле из 4.2; если появится общий доступ к проектам или команды, нужно будет решать, чей тариф действует (владельца, каждого участника или отдельное «место») |
| Организации платформы заявок с несколькими участниками (устаревший сценарий) | лимиты считаются по действующему пользователю, ответы — по владельцу организации; на standalone-сервисе это не встречается |
| Новые аккаунты ради повторного пробного периода | подтверждение почты и лимиты на регистрацию снижают риск, но не устраняют его |
| Отложенное удаление откладывает стирание персональных данных: при годовой подписке до 12 месяцев | проверить с юристом сроки, в которые закон требует удалять данные по требованию человека. Запасной вариант — вторая кнопка «Удалить сейчас, остаток не возвращается» рядом с «Согласен» (в плане не реализована, решение за владельцем) |
| Отложенное удаление не сработает, если за время периода появилась организация с участниками | воркер не удаляет, пишет событие `deletion_blocked` и просит пользователя разобраться с организацией |
| Пересчёт при смене тарифа посреди периода | в первой версии без пропорционального расчёта: повышение начинает новый период сразу, остаток прошлого не засчитывается |
| Часовые пояса | всё хранится и считается в UTC, период — по `timestamptz` |
| Единая точка отказа (один сервер, один воркер) | тик идемпотентен, повторный запуск ничего не ломает |
| Администратор видит email и телефон всех пользователей | роль выдаёт только CLI, проверка по БД, действия пишутся в `subscription_events`; держать число администраторов минимальным; уточнить с юристом основания доступа к персональным данным |

## 11. Решения

Решено:

- **Подписка на пользователя**, организации и места в биллинге не участвуют (решение владельца продукта, 2026-10-27).
- Тариф «Команда» из продукта убран.
- Администратор — роль `users.role = "admin"`; пока оплата ручная, тариф выдаётся по заявке пользователя через админку (раздел 6.1).
- «Исследователь» — единственный платный тариф, верхнего нет.
- Удаление аккаунта с оплаченным периодом: предупреждение, аккаунт активен до конца периода, затем удаляется при согласии пользователя; возврат остатка не предусмотрен (раздел 4.8).

Нужны до начала:

3. **Каталог тарифов в коде** (рекомендую для двух тарифов) или в таблице с админкой?
4. **Платёжный провайдер** — блокирует только этап 8.
5. **Бета-пользователи:** выдать «Исследователя» на срок через `grant-beta`? На какую дату?
6. ~~Список «базовых» методик для «Старта»~~ — решено 2026-10-27: Лайкерт, NPS, CSAT, когнитивное интервьюирование, вопросы-ловушки.
