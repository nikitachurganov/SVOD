## 1. Figma / FigJam MCP: что известно и что нет

### 1.1 Доступные инструменты (по описаниям в этой сессии)

| Инструмент | Что заявлено описанием | Статус проверки |
|---|---|---|
| `use_figma` | Запуск JS Plugin API в файле; работает для `/design/`, **`/board/` (FigJam)** и `/slides/`; лимит `code` — 50 000 символов; запрещены `setPluginData`, `loadAllPagesAsync`, `createImageAsync`; перед вызовом обязательно загрузить skill `figma-use` (для FigJam — `figma-use-figjam`) | ✅ **проверено 2026-10-22**: секции, shape-with-text (`ROUNDED_RECTANGLE`, `PREDEFINED_PROCESS`, `ELLIPSE`, `DIAMOND`, `HEXAGON`, `SQUARE`), коннекторы с подписями и пунктиром, таблицы, кириллица и эмодзи |
| `create_new_file` | Создаёт файл, `editorType: "figjam"`, нужен `planKey` из `whoami`; перед вызовом — skill `figma-create-new-file` | ❓ не вызывался |
| `whoami` | Возвращает планы пользователя (`planKey`) | ❓ не вызывался |
| `generate_diagram` | Mermaid → FigJam (flowchart, sequence, state, ER, gantt); **не умеет** управлять шрифтами и положением отдельных фигур; может создать файл или добавить в `fileKey` | ❓ не вызывался |
| `get_figjam`, `get_screenshot`, `get_metadata` | Чтение узлов FigJam и скриншоты — для проверки результата | ✅ `get_figjam` и `get_screenshot` работают; `get_metadata` для FigJam не поддерживается |
| `upload_assets`, `send_code_to_figma`, `get_design_context` | Не требуются для карты экранов | — |
| Сервер `plugin:figma:figma` | Сообщение среды: **требует авторизации** (OAuth на стороне пользователя) | ❓ состояние авторизации неизвестно |

### 1.2 Прецедент в репозитории

`docs/c4/build-figjam.js` — скрипт для запуска через `use_figma` («once per LEVEL», нативные редактируемые узлы). Он использует: страницу FigJam по жёсткому `getNodeByIdAsync('31:288')`, `figma.createSection()`, `createShapeWithText()` (`ROUNDED_RECTANGLE`, `ENG_DATABASE`), `createConnector()` с `connectorStart/End`, `ELBOWED`/`STRAIGHT`, стрелкой `ARROW_EQUILATERAL`, подписями на коннекторах, пунктиром для «планируется», шрифт Inter, идемпотентную обёртку по имени (`СВОД · C4 · 2026-10-14`), возврат `createdNodeIds` и `refs`. Это **доказывает, что подход применялся ранее**, но не доказывает, что он работает сейчас в этой сессии; точного id целевого файла в скрипте нет.

### 1.3 Что можно автоматизировать, а что нет

| Операция | Автоматизация | Основание | Что проверить в Stage 0 |
|---|---|---|---|
| Создать новую доску FigJam | Возможна | `create_new_file` | Выбор `planKey`; права; название |
| Секции, карточки, стикеры, коннекторы по JSON | Возможна | `use_figma` + прецедент `build-figjam.js` | Кириллица в Inter; ограничения числа узлов за вызов |
| Идемпотентное обновление по ID | Возможна через имена узлов (`setPluginData` запрещён) | Ограничение API | Поиск по `[ID]` в имени |
| Проверка результата | Возможна | `get_figjam`, `get_screenshot` | Формат ответа |
| Обзорные схемы (жизненный цикл заявки) | Частично, `generate_diagram` | Mermaid `stateDiagram` | Качество раскладки; не использовать для основной карты |
| Выбор целевой доски, авторизация OAuth | **Вручную** | Политика безопасности, права доступа | — |

| Согласование спорных решений (Q-02, Q-03 …) | **Вручную** | Решение продукта | — |

### 1.4 Промежуточный формат данных

Если запись в FigJam окажется недоступной, карта собирается ручными/полуавтоматическими средствами из тех же файлов: [screens.json](screens.json) (узлы, роли, статусы, US, расхождения) и [transitions.json](transitions.json) (рёбра). Описание полей — в приложении A.

### 8.3 Соединения и правила стрелок

Типы рёбер заданы полем `kind` в [transitions.json](transitions.json).

| `kind` | Что значит | Линия | Подпись |
|---|---|---|---|
| `route` | переход по маршруту (смена URL) | сплошная, `ELBOWED`, стрелка | `trigger` |
| `tab` | переключение вкладки | тонкая сплошная | название вкладки |
| `modal` | открытие модалки/drawer/popover | пунктир | `trigger` |
| `state` | смена состояния/статуса без смены экрана | точка-пунктир; для `workflow` — подпись `new → planning` | `trigger` |
| `auto` | автоматический переход или побочный эффект | сплошная + метка «auto» | `trigger` |
| `external` | выход за приложение/между каналами (письмо, Telegram, ссылка) | серый пунктир | `trigger` |
| `redirect` | клиентский/серверный редирект | сплошная + метка «redirect» | `trigger` |
| любая, `status ∈ {planned-spec, proposed}` | ведёт на несуществующий экран | **красный пунктир** | `trigger` (+ «🔵/🟣») |

Правила:

1. Направление: **слева направо и сверху вниз**; обратные стрелки только для реальных возвратов («Назад», «Закрыть»).
2. Один коннектор на уникальную тройку `(from, to, trigger)`; подпись ≤4 слов, условие — в тултипе/комментарии, не на линии.
3. **Самопереходы (`from == to`, 7 штук)** не рисуются коннектором: выводятся строкой `⟲ trigger (workflow)` в нижней части карточки (T-020, T-122, T-123, T-136, T-145, T-315, T-414).
4. Переходы вкладок рисуются внутри рамки родителя, не пересекая соседние модули.
5. Рёбра к `EXT-*` и между модулями — только в области 4, а не в области 2.
6. Входящие в модалку рёбра заканчиваются на её левой/верхней грани; исходящие — на правой/нижней (`magnet`).
7. Пересечения линий минимизируются порядком колонок; допустимые «длинные» рёбра — только в области 4.

### 8.4 Статус реализации и приоритет релиза

Цвет кодирует **только статус реализации**. Приоритет релиза кодируется **не цветом** — значком в углу карточки и в тексте.

### 8.5 Карточка экрана

Компактный шаблон (6 строк, ≤40 символов на строку; остальное — в комментарии/ссылке):

```
S-REQ-02 · Создание заявки
REQ · /requests/create
Роли: MEMBER, OWNER
✅ implemented · ·
US: —   BR-020
Действия: выбрать форму; сохранить
src/pages/CreateRequestPage.tsx
```

Поля карточки (из `screens.json`):

| Строка | Поле JSON | Правило |
|---|---|---|
| 1 | `id`, `title` | заголовок крупно; обрезается по ширине |
| 2 | `module`, `route` | `—` если маршрута нет |
| 3 | `roles` | убрать префикс `ROLE-`; >3 ролей → «+N» |
| 4 | `implementation.status`, `release_priority` | маркер статуса + значок приоритета |
| 5 | `sources.us`, `sources.br` | первые 3 ID, остальное «+N» |
| 6 | `actions` | первые 2–3 глагола |
| 7 | `implementation.evidence[0]` | только для статусов implemented/partial/code-orphan |

Для модалок и состояний — три строки (ID·название, статус·приоритет, родитель). У карточки в комментарии FigJam хранятся: полный список `evidence`, `notes`, `gap_refs`.

### 8.6 Система идентификации на доске

- Имя узла: `[<ID>] <Название>`; поиск при обновлении — по префиксу `[ID]` (так как `setPluginData` запрещён).
- Имя коннектора: `T-xxx`.
- Имя стикера: `GAP-xx` / `Q-xx`.
- Имя секции области: `AREA-N · …`.
- Результат каждого вызова `use_figma` (список созданных `nodeId` и таблица `refs`) сохраняется рядом с доской как `figjam-refs.json` — используется для обновлений и сверки (файл создаётся при сборке, в этой работе не создаётся).

Метод проверки полноты:

1. **Скрипт сверки JSON ↔ доска:** экспорт имён узлов доски (`get_figjam`) → сопоставление множества `[ID]` с `nodes[].id`; расхождение должно быть нулевым.
2. **Сверка с роутером:** множество `path:` из `src/App.tsx` ⊆ множества `route` в `nodes[]`.

### 10.3 Правила обновления доски

- Источник правды — JSON-файлы; доска — их визуализация.
- Изменение статуса/маршрута → правка JSON → повторный запуск скрипта по ID (идемпотентно) → сверка.
- После закрытия GAP: обновить `implementation.status`, перекрасить карточку, добавить или убрать рёбра, пометить стикер как закрытый (не удалять).
- Любой новый экран получает ID по схеме §8.6 и попадает в реестр до появления на доске.
