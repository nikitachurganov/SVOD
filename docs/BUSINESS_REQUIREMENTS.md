# СВОД — Бизнес-требования

Версия: 0.2 (черновик) · Дата: 2026-09-30

---
## 1. Цель и контекст
### 1.1. Проблема
Заявки приходят из разных источников: мессенджеры, почта, устные просьбы. Они теряются, приходят неполными из-за чего теряется часть контекста, возникают проблемы коммуникации, сроки затягиваются. Команда тратит время на переспрашивание и ручную координацию, а заявитель не знает, что происходит с его запросом.
### 1.2. Видение
СВОД превращает хаос входящих заявок в единый структурированный поток. Заявитель подаёт запрос через форму или Telegram. Система помогает сделать его (запрос) полным, определить куратора и ведёт заявку по понятному жизненному циклу до результата.
### 1.3. Ценность
- Все заявки в одном месте, у каждой есть подзадачи, статус и срок.
- Заявки приходят достаточно полными, поэтому доуточнений меньше.
- Заявитель и команда видят ход работы.

## 2. Целевая аудитория и стейкхолдеры

**Целевой клиент:** малые команды до 50 человек (маркетинг, продукт, агентства, внутренние сервисные команды), которым нужно принимать запросы от коллег, партнёров и клиентов. Продукт самодостаточен и не требует интеграций с корпоративными системами.

| Стейкхолдер                        | Интерес                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------- |
| Владелец бизнеса                   | Увеличение прибыли, укрепление партнерских отношений, минимизация убытков             |
| Участник (сотрудник)               | Понятные требования, понимание того, где находится информация по каждой задачи/заявке |
| Заявитель (внешний или внутренний) | Простой способ подать запрос без лишних вопросов                                      |
| Внешний подрядчик                  | Коммуникация в привычном формате                                                      |
| Владелец продукта                  | Сокращение потерянных заявок, рост качества заявок                                    |

## 3. Роли и права

### 3.1. Принципы
- **Владелец организации** — единственная фиксированная роль. Он обладает всеми правами и **сам назначает участникам доступ к модулям**.
- Остальные роли называются по **должностям** (например, «Маркетолог», «Проджект-менеджер», «Дизайнер»). Название роли ничего не определяет само по себе: права зависят только от того, к каким модулям владелец дал доступ. У двух людей с одной должностью доступы могут различаться.
- Ответственный по заявке и исполнитель задачи — не роли, а назначения внутри конкретной заявки. Куратором или исполнителем может быть любой участник.

### 3.2. Модули
Доступ выдаётся по модулям:

| Модуль | Содержание |
|---|---|
| Заявки | Реестры заявок, карточка заявки, этапы и задачи |
| Формы | Конструктор форм и публичные ссылки |
| Подрядчики | Справочник внешних подрядчиков |
| Участники | Список участников, приглашения, заявки на вступление |
| Настройки организации | Параметры организации, ссылка для вступления, включение AI |

Уровни доступа внутри модуля (например, просмотр и изменение) уточняются, см. раздел 10.

### 3.3. Права внутри заявки

| Действие | Владелец | Участник с доступом к «Заявки» | Куратор заявки | Исполнитель задачи |
|---|---|---|---|---|
| Взять свободную заявку (стать куратором) | + | + | — | — |
| Назначить или сменить куратора | + | — | — | — |
| Управлять статусом, планом и этапами заявки | + | — | + | — |
| Работать со своей задачей (статус, результат) | + | — | + | + |

Управление доступами к модулям, модерация заявок на вступление и настройки организации остаются у владельца, если он не открыл соответствующие модули другим участникам.

### 3.4. Вне организации
- **Заявитель** подаёт заявку без аккаунта, по публичной ссылке или через Telegram.
- **Внешний подрядчик** не пользователь системы. Требования ему передаются в канале, согласованном с ним (см. п. 5.5).

## 5. Бизнес-процессы

### 5.1. Приём заявки
1. Заявитель открывает публичную ссылку организации или пишет в Telegram-бота.
2. Если форм несколько, система помогает выбрать подходящую (в том числе в чат-формате).
3. Заявитель заполняет форму. Система подсвечивает пробелы и слабые места, которые с высокой вероятностью потребуют уточнения.
4. Заявка попадает в организацию со статусом «Новая» без куратора и уведомляет команду.

### 5.2. Жизненный цикл заявки

```
Черновик → Новая → Планирование → В работе → Завершена → Архив
                       ↑              ↓
              Ожидание уточнения ←────┘        Отменена → Архив
```

| Статус | Смысл |
|---|---|
| Черновик | Заявка ещё не отправлена |
| Новая | Принята, ждёт куратора и разбора |
| Планирование | Есть куратор, определяются этапы и исполнители |
| В работе | Задачи по этапам выполняются |
| Ожидание уточнения | Работа приостановлена, нужны данные от заявителя (возможно из «Новая», «Планирование», «В работе») |
| Завершена | Работа выполнена и закрыта. Отдельного статуса «закрыта» нет |
| Отменена | Заявка не будет выполняться |
| Архив | Хранение завершённых и отменённых заявок |

Из «Завершена» заявку можно вернуть в «Планирование», если результат не принят. Из «Ожидание уточнения» заявка возвращается в «Новая» или «Планирование».

### 5.3. Планирование: этапы и задачи
1. Куратор разбивает заявку на последовательные **этапы**. У этапа есть описание, ожидаемый результат и срок.
2. На этап назначается **исполнитель**: сотрудник организации или внешний подрядчик.
3. На основании этапа с назначенным исполнителем создаётся **задача**, которая присваивается конкретному человеку. Сотрудник видит её в своём списке задач.
4. Для задачи подрядчика требования передаются вне системы (п. 5.5), а статус и результат в СВОД фиксирует сотрудник.

Этап и задача — две стороны одной работы: этап отвечает на вопрос «что нужно сделать в плане заявки», задача — «кто конкретно это делает».

### 5.4. Назначение исполнителя
Система рекомендует исполнителей по специализации, загрузке, истории выполненных работ, географии и рейтингу. Окончательное решение принимает человек. Автоназначения нет.

### 5.5. Работа с внешним подрядчиком
Подрядчик получает требования **в канале, о котором с ним договорились** (по ходу переписки: почта, мессенджер и т. п.). СВОД не заменяет этот канал, а подготавливает материал и сокращает путь до него.

1. Куратор выбирает подрядчика из справочника; у подрядчика указан согласованный канал связи.
2. СВОД формирует готовый пакет требований по задаче.
3. Сотрудник одним действием переходит в почту или мессенджер, где требования уже подставлены, либо копирует их как текст, либо скачивает как файл и прикладывает сам.
4. Сотрудник отмечает в СВОД, что требования переданы.
5. Результат от подрядчика вносит сотрудник (файл или ссылка), после чего задача закрывается.

## 8. Ограничения и допущения

- Целевые организации небольшие (до 50 человек); права настраиваются по модулям владельцем, без сложной иерархии ролей.
- Внешний подрядчик не работает внутри СВОД; общение с ним идёт вне системы, в канале, согласованном с ним. СВОД готовит требования и ведёт учёт передачи.
- Заявитель, как правило, не имеет аккаунта.
- Первый мессенджерный канал приёма заявок — Telegram.
- AI зависит от внешнего поставщика LLM, поэтому качество и доступность не гарантируются, а функции должны деградировать без блокировки процесса.

## 9. Вне рамок

- Интеграции с Jira, 1С, CRM и другими корпоративными системами.
- Мобильное приложение (только адаптивный веб и Telegram).
- Аналитика и дашборды.
- Автоматическое назначение исполнителей и автономные действия AI.
- Отправка требований подрядчику самой системой от имени сотрудника (передача идёт через почту или мессенджер сотрудника).

**Открытые вопросы**
1. Числовые цели G1 и G2 (п. 4) — подтвердить или скорректировать.
2. Срок хранения удалённых заявок и сообщений групповых чатов (NFR-04, BR-064).
3. В каком формате скачивать пакет требований для подрядчика (текст, PDF, DOCX, Markdown) (BR-043).
4. Нужно ли заявителю видеть статус своей заявки (BR-028)?
5. Какие данные допустимо отправлять во внешний AI-сервис при сохранении требований 152-ФЗ (BR-078).
6. Какие уровни доступа нужны внутри модуля (просмотр, изменение, управление) и можно ли выдавать доступы не по одному человеку, а шаблоном на должность (BR-006).
7. Название назначения «куратор заявки» — рабочее, нужно утвердить.

**Риски**
| Риск | Влияние | Митигация |
|---|---|---|
| Внешний AI-провайдер расположен за рубежом | Конфликт с NFR-01 и NFR-02 | Не передавать ПДн (BR-078); при необходимости выбрать провайдера в РФ |
| Низкое качество AI-подсказок | Заявки всё равно уходят на доуточнение, G1 не достигается | Ручные правила проверки, человек подтверждает результат |
| Спам через публичную ссылку | Перегрузка команды и расходы на AI | Лимиты (BR-079, NFR-05), отключение ссылки |
| Команды не переходят на СВОД из привычных чатов | Часть заявок остаётся вне системы | Telegram-бот и создание заявки из переписки |
| Сотрудник забывает отметить передачу требований подрядчику или его ответ | Статус задачи не отражает реальность | Напоминания по сроку задачи (BR-027) |

## 11. Глоссарий

| Термин | Значение |
|---|---|
| Организация | Рабочее пространство команды: участники, формы, заявки |
| Владелец организации | Единственная фиксированная роль с полными правами; назначает участникам доступ к модулям |
| Участник | Член организации; роль названа по должности, права определяются выданными доступами |
| Модуль | Раздел продукта, к которому владелец выдаёт доступ (Заявки, Формы, Подрядчики, Участники, Настройки) |
| Заявка | Запрос на работу, поданный через форму или Telegram |
| Форма | Шаблон полей, по которому подаётся заявка |
| Публичная ссылка | Ссылка для подачи заявок без аккаунта |
| Куратор заявки | Участник, который ведёт заявку целиком; это назначение, а не роль. Название рабочее |
| Этап | Часть плана заявки: что нужно сделать, какой результат ожидается, к какому сроку |
| Задача | Работа, создаваемая на основании этапа и присваиваемая конкретному человеку |
| ТЗ | Требования к результату этапа, передаваемые исполнителю |
| Исполнитель | Сотрудник организации или внешний подрядчик, которому назначен этап |
| Подрядчик | Внешний исполнитель из справочника организации, не пользователь системы |
