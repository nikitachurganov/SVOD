# Условия в опросах: план

Статус: этап 1 сделан 2026-11-08 (не закоммичен). Отличия от плана ниже:

- Разный текст завершения сделан как **экран завершения**: обычная страница с `ending: true` и блоками «Текст без вопроса». На неё попадают только по переходу, при обычном порядке она пропускается.
- Проверки ссылок (переход назад, недоступная страница, неподключённый экран завершения, одинаковые названия вариантов) работают в редакторе, а не в `survey_linter.py`. Сервер неверные переходы просто игнорирует и идёт по порядку.
- Код: `src/shared/survey-logic/` (правила, навигация, помощники редактора), `backend/app/services/survey_logic.py`, общие примеры `backend/tests/fixtures/survey_logic_cases.json` (`npm run test:logic` и `pytest tests/test_survey_logic.py`).
- ИИ‑конструктор про переходы пока не знает: при правке опроса через ИИ переходы могут потеряться (этап 3).

## Что нужно

Автор опроса хочет, чтобы опрос шёл по‑разному в зависимости от ответов: «выбрал А — сценарий 1, выбрал Б — сценарий 2, выбрал В — сценарий 3». Это не новый тип поля, а правила, которые навешиваются на уже существующие вопросы.

Сейчас условий нет совсем: страницы идут подряд (`PublicSurveyPage.tsx`, `pageIndex + 1`), сервер требует ответ на каждый обязательный вопрос (`survey_answers.validate_answers`).

## Рекомендация: два вида правил, сценарий = страница

У конкурентов это две разные вещи, и нам нужны обе, но в разном порядке.

**1. Переход по ответу (главное, делать первым).** На вопросе с одним вариантом ответа (`radio`, `dropdown`, `yesNo`) у каждого варианта можно выбрать, куда идти дальше: на какую страницу или «завершить опрос». Сценарий в этой модели — это страница или цепочка страниц. Так это сделано в Google Формах («перейти к разделу в зависимости от ответа»), в Typeform (Logic jumps) и в SurveyMonkey (Skip logic). Ровно то, что описано в запросе.

**2. Показ по условию (вторым этапом).** У отдельного вопроса задаётся «показывать, если…»: например, «Почему такая оценка?» показывается, только если NPS ниже 7, или «Чем пользуетесь?» — только если в предыдущем вопросе отмечен вариант «Другое». Это нужно для вопросов с несколькими ответами, чисел и оценок, где «перейти на страницу» неудобно.

Почему не одно универсальное «если — то» на всё сразу: такой редактор сложен для автора и для проверки на сервере. Переходы по страницам закрывают основной запрос и понятны без объяснений, показ по условию добавляется поверх той же проверки условий.

### Ограничения, которые снимают большую часть проблем

- Переход только **вперёд** (на страницу ниже текущей или в конец). Тогда в опросе не бывает циклов, а путь респондента всегда однозначно вычисляется из его ответов.
- Условие может ссылаться только на вопрос, который стоит **раньше**.
- У каждой страницы есть «после этой страницы»: по умолчанию следующая, можно выбрать другую или конец. Без этого ветки не сходятся: сценарий 1 закончился, а дальше идёт сценарий 2.
- Если на странице несколько вопросов с переходами, срабатывает первый сверху, у которого задан переход для выбранного ответа. Иначе — переход страницы по умолчанию.

## Как хранить

Всё ложится в текущую схему `pages`, миграция базы не нужна (схема и так JSON).

```ts
// Вопрос с одним вариантом ответа
field.config.jumps = { [optionId]: pageId | 'end' }

// Страница
page.next?: pageId | 'end'          // нет — значит следующая по порядку

// Этап 2: показ вопроса по условию
field.visibleIf?: {
  match: 'all' | 'any',
  rules: Array<{
    fieldId: string,
    op: 'is' | 'isNot' | 'includes' | 'lt' | 'gt' | 'answered',
    value?: string | number | string[],
  }>,
}
```

Ссылки идут по `id` вопросов, вариантов и страниц, как и ответы. Переименование ничего не ломает.

## Что меняется

### Прохождение опроса (`PublicSurveyPage.tsx`, `FormFillRenderer`)

- «Далее» считает следующую страницу по правилам, а не `+1`. Пройденные страницы складываются в историю, «Назад» идёт по ней.
- Кнопка «Отправить ответы» появляется, когда следующая точка — конец, а не только на последней странице.
- Прогресс: длина пути заранее неизвестна. Показываем «Шаг N из M», где M — длина пути при текущих ответах. Число может меняться, это нормально.
- Перед отправкой ответы со страниц, которые не попали в путь, и со скрытых вопросов выбрасываются. Иначе респондент вернулся, сменил ответ, а старая ветка уехала на сервер.
- Этап 2: скрытие вопроса внутри страницы — через `x-reactions` Formily или фильтрацию полей перед `pageToFormilySchema`. Нужно проверить и на старом рендере `LegacyFormFill`.

### Сервер (`survey_answers.py`, `survey_results.py`)

- Одна функция `visible_path(pages, answers)`: повторяет путь респондента по его ответам и возвращает показанные вопросы. Та же логика есть на фронте, поэтому общий набор примеров в JSON проверяет обе реализации одинаково.
- `validate_answers`: обязательность проверяется только у показанных вопросов, ответы на непоказанные отбрасываются.
- `quality_flags`: порог «слишком быстро» считается от числа показанных вопросов, а не всех.
- Результаты: у вопроса из ветки процент считается от тех, кому его показали. В карточке вопроса писать «показан 40, ответили 38», иначе кажется, что 60 % пропустили вопрос.
- `_completion_rate` — по показанным вопросам.
- `structure_conflicts`: менять переходы после первых ответов можно (смысл собранных ответов не меняется). Удаление варианта уже запрещено, удаление страницы, на которую ведёт переход, — предупреждение в редакторе.

### Редактор (`FormEditor.tsx`, `FieldBlock`, `FieldTypeSettings.tsx`)

- У вопроса с одним вариантом — раздел «Переходы»: список вариантов, у каждого выпадающий список «Дальше: следующая страница / Страница 3 «Для клиентов» / Завершить опрос».
- У страницы — «После этой страницы: …».
- Метки на карточках: «Есть переходы» на вопросе, «Сюда ведут: Вопрос 2 → Б» на странице. Без них через неделю автор не поймёт, почему опрос идёт так.
- Проверки перед публикацией (в `survey_linter.py` или на фронте): переход на удалённую страницу или вариант, страница, на которую нельзя попасть, условие на вопрос ниже по опросу.
- Предпросмотр сейчас позволяет листать страницы без ответов. С переходами в предпросмотре нужно проходить по веткам, иначе автор не проверит сценарии. Предложение: в предпросмотре переходы работают, а над формой есть «Показать все страницы подряд».
- Позже: схема опроса на одном экране (страницы и стрелки переходов). Не для первого этапа.

### ИИ‑конструктор (`survey_ai_builder_service.py`)

Описать в подсказке формат `jumps` и `page.next`, чтобы ИИ мог собирать опрос со сценариями («скрининг: клиент — одна ветка, не клиент — другая»). Ответ ИИ прогонять через ту же проверку ссылок.

## Этапы

1. **Переходы по ответу.** Хранение, расчёт пути на фронте и сервере с общими примерами, прохождение с историей, валидация и очистка ответов, редактор переходов на вопросе и странице, проверки ссылок. Результаты: «показан / ответили».
2. **Показ вопроса по условию.** `visibleIf` на вопросах (и группах), условия по нескольким ответам, числам, оценкам, «ответил / не ответил».
3. **Удобство.** Схема переходов, переходы в ИИ‑конструкторе, фильтр результатов по ветке («только те, кто ответил А»), шаблоны со сценариями.

## Что решить до начала

1. Сценарий — это страница? Рекомендация: да. Альтернатива — переход к конкретному вопросу, но тогда опрос по одному вопросу на экран, а у нас страницы с несколькими вопросами.
2. Переходы только по вопросам с одним ответом на первом этапе? Рекомендация: да; несколько ответов, числа и оценки — во втором этапе через показ по условию.
3. Условия — во всех тарифах или в платных? Сейчас этого нет в `docs/TARIFFS_FINAL.md`.
4. Нужно ли в первом этапе завершение опроса с разным текстом («Спасибо, вы нам не подходите» для отсеянных скринингом)? Это частый запрос к ветвлению, добавляется небольшим полем `endScreen` у перехода в конец.
