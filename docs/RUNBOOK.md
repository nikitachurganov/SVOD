# Runbook — СВОД (production)

Операционная памятка для `app.svodservice.ru`. Первичная установка, DNS и SSL подробно описаны в [DEPLOYMENT_VPS.md](./DEPLOYMENT_VPS.md) — здесь только повседневные действия. Переменные окружения — в [ENV.md](./ENV.md).

Все команды выполняются на VPS в `/opt/svod`. Для краткости:

```bash
alias dc='docker compose -f docker-compose.production.yml'
```

## Сервисы

| Сервис | Что делает | Порты | Healthcheck |
|--------|------------|-------|-------------|
| `nginx` | Единственная точка входа: `/api/*` → `api`, остальное → `frontend` | 80, 443 | зависит от `frontend` и `api` |
| `frontend` | Статика SPA | внутренний | `wget http://127.0.0.1/` |
| `api` | FastAPI | внутренний 8000 | `curl http://localhost:8000/health` |
| `migrate` | `alembic upgrade head`, затем завершается | — | — |
| `worker` | Фоновый ИИ-анализ заявок, просрочки этапов; метрики на :9101 | внутренний | нет |
| `telegram-bot` | Long polling Telegram, ровно один экземпляр | нет | нет |
| `db` | PostgreSQL 16, volume `pgdata` | внутренний | `pg_isready` |

## Деплой

```bash
cd /opt/svod
git pull
dc up -d --build          # весь стек; миграции применит сервис migrate
dc ps                     # все сервисы Up, api и frontend — healthy
curl -s https://app.svodservice.ru/api/health   # {"status":"ok"}
```

Только backend: `dc up -d --build api worker telegram-bot`. Только frontend: `dc up -d --build frontend nginx`.

После деплоя пройдите чек-лист из [DEPLOYMENT_VPS.md](./DEPLOYMENT_VPS.md#12-чеклист-готовности): логин, создание заявки.

## Мониторинг

| Что | Где |
|-----|-----|
| Здоровье API | `GET /api/health` → `{"status":"ok"}` |
| Метрики API | `GET /metrics` (Prometheus) |
| Метрики worker | порт 9101 внутри сети Compose |
| Логи | `dc logs -f --tail=200 api` (аналогично `worker`, `telegram-bot`, `nginx`) |

Метрики приложения: `svod_request_api_errors_total{method,status}`, `svod_ai_job_duration_seconds{kind,outcome}`, `svod_ai_job_retries_total{kind}`, `svod_s3_errors_total{operation}`, `svod_overdue_stages`, `svod_notification_skipped_total{type}`.

> **Риск.** Nginx проксирует весь `/api/*` в backend, поэтому `/metrics` backend доступен снаружи как `https://app.svodservice.ru/api/metrics`. Закройте этот путь в `deploy/nginx/*.conf`, если метрики не должны быть публичными.

Сбор метрик, дашборды и Alertmanager в репозитории **не настроены** (нет конфигурации Prometheus/Alertmanager/Grafana). Взамен `worker` сам следит за тем, что тихо останавливает платный сервис, и пишет на `ADMIN_NOTIFY_EMAIL` и в лог (`ERROR … Ops alert`): ИИ не отвечает, суточный потолок расходов на ИИ, кредиты OpenRouter, платежи не создаются или висят. Какие оповещения и что делать — в [LAUNCH_CHECKLIST.md](./LAUNCH_CHECKLIST.md), раздел 2. Упавший `worker` или `api` эти оповещения не пришлют: нужна внешняя проверка `/api/health` (там же, раздел 1).

## Почта на домене svodservice.ru (REG.RU)

Основной вариант. Настройки из личного кабинета REG.RU: сервер исходящей почты `mail.hosting.reg.ru`, порт SSL/TLS `465`, логин — полный адрес ящика.

1. В кабинете REG.RU создайте ящик (сейчас `support@svodservice.ru`) и задайте ему длинный случайный пароль.
2. Убедитесь, что у домена есть записи MX, SPF и DKIM (если DNS на серверах REG.RU, они добавляются при подключении почты; DKIM включается в панели почты) и запись DMARC: TXT на `_dmarc` со значением `v=DMARC1; p=none; rua=mailto:<адрес>`. Без SPF и DKIM письма попадают в «Спам».
3. В `backend/.env` хост, порт и SSL уже заданы, впишите:
   ```
   SMTP_USERNAME=support@svodservice.ru
   SMTP_PASSWORD=<пароль ящика>
   SMTP_FROM=support@svodservice.ru
   APP_PUBLIC_URL=https://<адрес сервиса>
   SURVEYS_APP_PUBLIC_URL=https://<адрес сервиса опросов, если он отдельный>
   ```
   `SMTP_FROM` должен совпадать с `SMTP_USERNAME`. `APP_PUBLIC_URL` нужен, иначе в письмах будут ссылки на `localhost`.
4. Перезапустите API (`dc up -d api`; в разработке `docker compose up -d --build api`) и проверьте отправку командой из раздела про Яндекс ниже: `True` — письмо ушло, `False` — причина в `dc logs api`.
5. Откройте полученное письмо в Gmail → «Показать оригинал»: SPF и DKIM должны быть PASS.

## Запасной вариант: почта через Яндекс 360

Письма подтверждения почты, восстановления пароля и приглашений уходят по SMTP. Пока нет ящика на `@svodservice.ru`, можно отправлять с обычного ящика Яндекса.

1. Заведите отдельный ящик для рассылки (например, `svod.noreply@yandex.ru`), не личный.
2. Включите двухфакторную защиту: пароли приложений в Яндекс ID доступны только с ней.
3. Создайте пароль приложения: id.yandex.ru → Безопасность → «Пароли приложений» → тип «Почта». Он показывается один раз.
4. Разрешите SMTP: Почта → Настройки → «Почтовые программы» → включите «С сервера imap.yandex.ru по протоколу IMAP» и разрешите пароли приложений. Для ящика в организации Яндекс 360 то же делает администратор в консоли (Почта → Доступ к ящикам по протоколам).
5. В `backend/.env` заполните (хост, порт и SSL уже заданы):
   ```
   SMTP_USERNAME=svod.noreply@yandex.ru
   SMTP_PASSWORD=<пароль приложения, не пароль от ящика>
   SMTP_FROM=svod.noreply@yandex.ru
   APP_PUBLIC_URL=https://<адрес сервиса>
   SURVEYS_APP_PUBLIC_URL=https://<адрес сервиса опросов, если он отдельный>
   ```
   `SMTP_FROM` обязан совпадать с `SMTP_USERNAME`: Яндекс отклоняет чужого отправителя. `APP_PUBLIC_URL` нужен, иначе в письмах будут ссылки на `localhost`.
6. Перезапустите API: `dc up -d api` (в разработке `docker compose up -d --build api`).
7. Проверьте отправку: `dc exec api python -c "import asyncio; from app.services import email_service as e; print(asyncio.run(e.send_email(to='ВАШ@АДРЕС', subject='Проверка', text='Работает')))"`. `True` — письмо ушло; `False` — причина в `dc logs api`.

Ограничения: у бесплатного Яндекса есть суточный лимит получателей (порядка 500), письма с чужого домена чаще попадают в «Спам». Когда появится `@svodservice.ru`, поменяйте только `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` (и добавьте SPF и DKIM для домена).

## Администратор платформы

Роль администратора хранится в `users.role`. Назначить её через API нельзя, только командой на сервере. Аккаунт должен уже существовать и быть активным:

```bash
dc exec api python -m app.billing_cli make-admin почта@пример.рф
```

Повторный запуск безопасен: если роль уже есть, команда об этом сообщит. Снять роль пока можно только запросом к БД:

```bash
dc exec db psql -U postgres myapp -c "UPDATE users SET role = 'user' WHERE email = 'почта@пример.рф'"
```

Дальше администратор работает в интерфейсе: меню профиля → «Администрирование» (`/admin` в сервисе опросов). Там три вкладки:

- **Пользователи**: таблица с поиском и фильтрами; по клику карточка с тарифом, использованием, журналом, расходом ИИ и действиями (заблокировать аккаунт, выключить ИИ, выдать или снять тариф, личные лимиты).
- **Заявки на тариф**: человек просит тариф, вы получаете письмо на `ADMIN_NOTIFY_EMAIL`, договариваетесь об оплате по контакту из заявки и после поступления денег нажимаете «Активировать». Человеку уходит письмо. Повторное нажатие или двое администраторов одновременно тариф дважды не выдадут.
- **Сводка**: пользователи, тарифы, ожидаемая выручка, расход на ИИ и его доля.

Тариф с карточки можно снять только если у человека не запланировано удаление аккаунта (оно сработает по окончании тарифа). Заблокированного человека система разлогинивает сразу, данные остаются.

Если у владельца опросов ответов сверх квоты тарифа (они сохраняются, но скрыты), после повышения тарифа или лимитов их открывает команда:

```bash
dc exec api python -m app.billing_cli unlock-responses почта@пример.рф
```

Она открывает все скрытые ответы владельца и пишет событие `responses_unlocked` в журнал подписки; повторный запуск ничего не меняет. Сколько ответов ждёт, видно в `GET /billing/subscription` (`usage.locked_responses`) или запросом `SELECT count(*) FROM survey_responses WHERE locked`.

## Тарифы вручную и worker

Пока оплаты нет, тариф выдают командами (каждая пишет событие `manual_grant` и открывает скрытые ответы):

```bash
dc exec api python -m app.billing_cli grant почта@пример.рф --days 30 --note "счёт 42"
dc exec api python -m app.billing_cli grant почта@пример.рф --until 2026-12-31
dc exec api python -m app.billing_cli show почта@пример.рф
```

`--days` прибавляется к действующему периоду, `--until` ставит дату (и не сокращает более длинный период). `show` ничего не меняет: тариф, статус, период, использование, скрытые ответы, последние события.

Бета-доступ для всех активных аккаунтов сначала проверьте без записи, потом выдайте:

```bash
dc exec api python -m app.billing_cli grant-beta --until 2026-12-15 --dry-run
dc exec api python -m app.billing_cli grant-beta --until 2026-12-15
```

Раз в `BILLING_TICK_SECONDS` (по умолчанию 5 минут) `worker` при `BILLING_ENABLED=true`: переводит закончившиеся подписки и пробные периоды на «Старт» (опросы сверх трёх закрываются, ничего не удаляется), шлёт напоминания и предупреждения о 80 % лимита, удаляет аккаунты, у которых закончился оплаченный период после просьбы об удалении. Что он сделал, пишет `dc logs worker` (строки `Billing tick`). Если `worker` не запущен, подписки не заканчиваются и письма не уходят.

Перед запуском и после него:

```bash
dc exec api python -m app.billing_cli preflight                          # всё ли готово; код выхода 1, если нет
dc exec api python -m app.billing_cli reset-response-counters --dry-run  # счётчик ответов из теневого режима
dc exec api python -m app.billing_cli funnel --days 30                   # как далеко дошли зарегистрировавшиеся
```

Порядок включения лимитов и откат — [LAUNCH_CHECKLIST.md](./LAUNCH_CHECKLIST.md).

Роль читается из БД при каждом запросе, поэтому снятие действует сразу. Дальше по плану: админка (`/admin`) и тарифы, см. [BILLING_BACKEND_PLAN.md](./BILLING_BACKEND_PLAN.md).

## Приём платежей (ЮKassa, самозанятый)

Онлайн-оплата включается, когда заданы `BILLING_ENABLED=true`, `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`. Без них остаётся только заявка на счёт, как раньше.

**Подключение магазина**

1. Нужен статус самозанятого (приложение «Мой налог»). Заявка на подключение ЮKassa для самозанятых — на [странице ЮKassa](https://yookassa.ru/ekvayring-dlya-samozanyatyh/), договор заключается онлайн. Там же сказано, что нужны паспорт, ИНН и кошелёк ЮMoney.
2. В личном кабинете ЮKassa, «Интеграция»: взять `shopId` и секретный ключ, прописать в `backend/.env` как `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`. Начните с тестового магазина: его платежи в сервисе помечены «Тест» и не входят в «Получено онлайн».
3. В «Интеграция → HTTP-уведомления» указать адрес `https://surveys.svodservice.ru/api/billing/webhooks/yookassa` и события `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Адрес должен быть HTTPS (порт 443 или 8443).
4. Перезапустить `api` и `worker`: `dc up -d api worker`.
5. Оплатить тестовой картой из документации ЮKassa. Проверьте: вкладка «Подписка» показывает «Оплата прошла, тариф включён», в админке в карточке человека на вкладке «Платежи» платёж «Оплачен» с отметкой «Тест».
6. Для боевого магазина замените ключи и повторите проверку одним настоящим платежом на минимальную сумму.

**Как это устроено.** Человек нажимает «Оплатить», получает страницу ЮKassa, платит и возвращается на вкладку «Подписка». Тариф включается по данным, которые сервер сам запрашивает у API ЮKassa, а не по тому, что сообщило уведомление или браузер: поддельное уведомление ничего не выдаёт. Платёж включает тариф один раз, сколько бы уведомлений ни пришло. Если уведомление потерялось, worker сам спросит ЮKassa о неоплаченных платежах (через 2 минуты после создания, затем на каждом тике). Оплаченный срок добавляется к действующему.

**Подписка не продлевается сама.** Автосписаний нет: когда срок подходит к концу, человеку приходит напоминание (за 3 дня), и он платит ещё раз.

**Возврат.** Делается в кабинете ЮKassa. В сервисе появится событие `payment_refunded` в карточке, а на `ADMIN_NOTIFY_EMAIL` придёт письмо. Тариф при этом остаётся: если он больше не положен, снимите его в карточке («Снять тариф»).

**Что уточнить в ЮKassa до запуска.** Их документация местами противоречит друг другу, а за них решать нельзя:

- **Чеки.** Самозанятый обязан выдавать чек на каждую оплату. Страницы ЮKassa пишут, что чек формируется автоматически через связку с «Мой налог» (для этого в кабинете нужно включить отправку чеков и подтвердить запрос в «Мой налог», за услугу может быть комиссия), но в стороннем источнике сообщалось, что автоматическая фискализация для самозанятых отключена. Спросите у поддержки ЮKassa (для вопросов по интеграции они указывают b2b_support@yoomoney.ru), как это работает именно у вас. Сервис чеки в ЮKassa не передаёт: если связка не включена, чек нужно формировать в «Мой налог» самому.
- **Комиссия** и **автоплатежи** для самозанятых: автосписания в сервисе не используются, пока это не выяснено.
- **Лимит дохода** на НПД 2,4 млн ₽ в год: сводка в админке («Получено онлайн» за 30 дней) помогает за ним следить.

## Расход на ИИ

Каждое ИИ-действие опросов (конструктор, резюме, чат) пишет в `ai_usage_log` токены и стоимость, которую вернул OpenRouter. Реальная цена действий по типам за последние 30 дней:

```bash
dc exec db psql -U postgres myapp -c "SELECT action, count(*) AS n, round(avg(prompt_tokens)) AS avg_in, round(avg(completion_tokens)) AS avg_out, round(avg(cost_usd), 5) AS avg_usd, round(sum(cost_usd), 2) AS total_usd FROM ai_usage_log WHERE created_at > now() - interval '30 days' GROUP BY action ORDER BY total_usd DESC"
```

Эти цифры заменяют оценки из [PRICING_TARIFFS.md](./PRICING_TARIFFS.md) (раздел 3). Те же данные есть в Prometheus: `svod_ai_tokens_total`, `svod_ai_cost_usd_total`, `svod_ai_actions_total`, а в теневом режиме ещё `svod_billing_limit_hit_total{enforced="false"}` показывает, сколько запросов лимит заблокировал бы. Защита от неожиданного счёта — `AI_DAILY_BUDGET_USD`.

## Частые проблемы

| Симптом | Причина и действие |
|---------|--------------------|
| `400` на `OPTIONS` в браузере | Origin не в `CORS_ORIGINS` (`backend/.env`). Добавьте домен JSON-списком и перезапустите `api` |
| `getaddrinfo failed` при запуске `alembic` на хосте | В `DATABASE_URL` указан хост `db` — он существует только внутри Docker-сети. На хосте используйте `localhost` |
| `api` не стартует, ошибка валидации настроек | Не задан `OPENROUTER_API_KEY` или `OPENROUTER_MODEL` (обязательны и не пустые) |
| Compose: `Set POSTGRES_PASSWORD in .env` | Не заполнен корневой `.env` |
| ИИ отвечает «ИИ-сервис недоступен» / «пустой ответ» (HTTP 502) | Проверьте `OPENROUTER_API_KEY`, баланс и доступность модели; ищите `OpenRouter HTTP error` в `dc logs api` |
| `429` на запросах ИИ по опросам | Лимит запросов на пользователя (40 за 180 с, в памяти процесса, общий для конструктора, резюме и чата); подождите, перезапуск `api` сбрасывает счётчик |
| `403` «Подтвердите адрес почты» в ИИ-конструкторе опросов | Почта аккаунта не подтверждена. Проверка действует только при заданном `SMTP_HOST` (без него письмо не уходит и подтвердить нельзя). Повторное письмо: `POST /auth/me/email-verification` |
| `503` «ИИ временно недоступен» (`ai_budget_exceeded`) | Достигнут `AI_DAILY_BUDGET_USD` за последние 24 часа. Посмотрите расход запросом из раздела «Расход на ИИ»; поднимите потолок или подождите, пока старые записи выйдут из окна |
| `402` `limit_reached` | Лимит тарифа при `BILLING_ENFORCE=true`. Поле `limit` в ответе: `ai_tokens` (токены ИИ закончились; `resets_at = null` для бесплатной квоты, которая не обновляется), `active_surveys`, `projects`, `questions`, либо `feature` с полем `feature` (`crosstabs`, `csv_export`, `methodology`). Использование пользователя видно в `GET /billing/subscription`. Сколько раз лимит сработал или сработал бы, показывает метрика `svod_billing_limit_hit_total`. Чтобы временно снять блокировку, поставьте `BILLING_ENFORCE=false` |
| Владелец опроса пишет, что ответов меньше, чем пришло | Квота ответов тарифа: ответы сверх `responses_per_period` сохраняются скрытыми (`locked`) при `BILLING_ENFORCE=true`. Респондент ошибки не видит. Скрытые ответы открывает повышение тарифа и команда `unlock-responses` (раздел «Администратор платформы»). Пока `BILLING_ENFORCE=false`, ответы только считаются |
| Тариф закончился, а опросы всё ещё открыты и письма нет | Тик worker не работает: проверьте, что `worker` запущен, `BILLING_ENABLED=true`, и `dc logs worker` на строки `Billing tick`. Дату окончания видно командой `billing_cli show` |
| Письма о тарифе (напоминания, окончание, удаление аккаунта) не приходят | Пустой `SMTP_HOST`: письма отключены, а напоминания помечаются обработанными. Иначе смотрите `dc logs worker` на `Failed to send email`: неудавшиеся напоминания и предупреждения повторяются на следующем тике, письмо об окончании тарифа не повторяется |
| Человек просил удалить аккаунт, а он остался после даты | Аккаунт удаляется только если нет организаций с другими участниками: тогда флаг снимается, а человеку уходит письмо (событие `deletion_blocked` в `billing_cli show`). Либо оплаченный период продлили, и дата сдвинулась |
| `403` `ai_disabled` | ИИ выключен для аккаунта (`users.ai_enabled = false`). Включить: `UPDATE users SET ai_enabled = true WHERE email = '…'` |
| Человек заплатил, а тариф не включился | В админке в карточке человека, вкладка «Платежи»: статус платежа и «ID в ЮKassa». «Ждёт оплаты» — ЮKassa ещё не подтвердила платёж (проверьте его в кабинете). Тариф включится сам: уведомление придёт повторно в течение суток, а worker сверяется каждые `BILLING_TICK_SECONDS`. «Сумма не совпала» — тариф намеренно не выдан, разберитесь в кабинете ЮKassa |
| Уведомления ЮKassa не доходят, в логе `api` «notification from an unknown address» | Прокси не передаёт настоящий адрес (`X-Real-IP`) или адреса ЮKassa изменились. Временное решение: `YOOKASSA_VERIFY_WEBHOOK_IP=false`, платёж всё равно проверяется через API |
| Кнопка оплаты отвечает «Не удалось создать платёж» | `dc logs api` на «YooKassa refused»: неверные ключи или в магазине не включён способ оплаты. «YooKassa is unavailable» — ЮKassa недоступна, повторите позже |
| ИИ-анализ заявок не выполняется | `AI_JOBS_ENABLED=true`? `dc logs worker`; зависшие задачи подхватываются через `AI_JOB_STALE_SECONDS` |
| Файлы не загружаются / не открываются | `S3_PUBLIC_ENDPOINT_URL` должен быть доступен браузеру (signed URL); смотрите `svod_s3_errors_total` |
| Письма-приглашения не уходят | Пустой `SMTP_HOST` — письма отключены, ссылку активации копируют из интерфейса. Иначе проверьте `SMTP_*` и `dc logs api` |
| Бот молчит, в логе «простаивает» | Заданы не оба значения `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME`. В группах бот видит сообщения только при отключённом privacy mode (`/setprivacy` → Disable в @BotFather) |
| После переключения на HTTPS nginx не стартует | Нет сертификатов в volume `certbot_certs` — см. раздел 8 в [DEPLOYMENT_VPS.md](./DEPLOYMENT_VPS.md) |
| Установка backend на Windows падает на `link.exe` | Python 3.14: нет колёс для `asyncpg`/`pydantic-core`. Используйте 3.12 (`backend/install-deps.ps1`) |

## Откат

Откат только кода (схема БД не менялась):

```bash
cd /opt/svod
git log --oneline -5                 # выбрать предыдущий рабочий коммит
git checkout <commit>                # или git revert <плохой коммит>
dc up -d --build
```

Откат вместе с миграцией БД. Сервис `migrate` умеет только вверх, а файл миграции есть лишь в новой версии кода, поэтому миграцию откатывают **до** переключения на старый код:

```bash
dc exec db pg_dump -U postgres myapp > /opt/svod-backup-$(date +%F).sql   # дамп перед откатом
dc stop api worker telegram-bot
dc run --rm api alembic current                  # какая ревизия применена
dc run --rm api alembic downgrade -1             # на одну миграцию назад (в образе новой версии)
git checkout <commit>
dc up -d --build
```

Миграции с удалением колонок или таблиц необратимы по данным — без дампа не откатывайте.

Автоматические бэкапы БД: скрипт `scripts/backup-db.sh` (сжатый `pg_dump`, проверка файла, хранение 14 дней) запускается из cron на VPS, строка и проверка восстановления — в [LAUNCH_CHECKLIST.md](./LAUNCH_CHECKLIST.md), раздел 1. Сам по себе cron не настроен: его нужно добавить на сервере.

## Дополнительно

- Ручной запуск миграций: `dc exec api alembic upgrade head`
- Текущая ревизия БД: `dc exec api alembic current`
- Перезапуск одного сервиса: `dc restart api`
- Локальная проверка перед деплоем: `npm run lint`, `npm run build`, `dc config`, `dc build` (см. [CONTRIBUTING.md](./CONTRIBUTING.md))
